Self-Hosted Runner Setup

Installing a GitHub Actions runner directly on the dev box, so the deploy step in ci.yml can run docker compose locally — no SSH key, no inbound network path.

Repo: Linkify-Solutions-Inc/kubernetes-streaming Box: kubernetes-server Runner user: gha-runner
Steps
1 Get a token 2 Restricted user 3 Copy secrets 4 Download + configure 5 Install as service 6 CPU constraint 7 Start + confirm

A small program runs on the box itself, polls GitHub for queued jobs labeled self-hosted, and executes them locally — that's what lets the deploy job in ci.yml run docker compose directly on the box. Everything below runs on the box (ssh kubernetes-server first), except step 1's token, which you generate from your own machine.

01

Get a registration token

your laptop

A short-lived (~1hr) credential that lets a machine register itself as a runner for this repo — nothing more. 

gh api -X POST repos/Linkify-Solutions-Inc/kubernetes-streaming/actions/runners/registration-token --jq '.token'

Copy the token it prints. If it expires before you finish, just re-run this.

02

Create a dedicated, restricted user

on the box
Why — the runner executes whatever a workflow tells it to (today just docker compose, but that's still real capability). A dedicated account limits the blast radius if a workflow ever does something unexpected — it should never run as your own fatima account or as root. 
ssh kubernetes-server
sudo useradd -m -s /bin/bash gha-runner
sudo usermod -aG docker gha-runner

docker group membership is the only privilege it gets — no sudo. That's enough to run docker compose, nothing else.

03

Copy today's secrets to where the runner can read them

on the box

The runner's job checks out a fresh copy of the repo each run — it won't have your gitignored .env. ci.yml's deploy step expects it at /home/gha-runner/streaming-project.env: 

sudo cp ~/streaming-project/.env /home/gha-runner/streaming-project.env
sudo chown gha-runner:gha-runner /home/gha-runner/streaming-project.env
sudo chmod 600 /home/gha-runner/streaming-project.env
04

Download and configure the runner

on the box
Why this version — v2.336.0 is GitHub's current release as of today; the sha256 below is checked against GitHub's published value rather than assumed.

as gha-runner:

sudo -iu gha-runner
mkdir actions-runner && cd actions-runner
curl -o actions-runner-linux-x64-2.336.0.tar.gz -L https://github.com/actions/runner/releases/download/v2.336.0/actions-runner-linux-x64-2.336.0.tar.gz
echo "04cf0be1aff4c3ec3554466c39124ca250e3effd8873bb7e8d68535aa9505d5d  actions-runner-linux-x64-2.336.0.tar.gz" | sha256sum -c
tar xzf actions-runner-linux-x64-2.336.0.tar.gz

sha256sum -c should print OK — confirms the download wasn't corrupted or tampered with.

register it (paste your token from step 1):

./config.sh --url https://github.com/Linkify-Solutions-Inc/kubernetes-streaming --token <YOUR_TOKEN> --name kubernetes-server --labels self-hosted,linux,streaming-project --unattended

--unattended skips interactive prompts; the --labels aren't load-bearing yet (the workflow just targets the built-in self-hosted label) but they're there if you ever add a second runner and want to target this one specifically.

leave the gha-runner shell:

exit
05

Install it as a systemd service

on the box
Why a service — a foreground process dies when your SSH session ends. systemd keeps it running, restarts it on crash, and starts it on boot.
Why one sudo command — gha-runner's home directory is private by default (mode 0750/0700), so a plain cd as fatima gets denied — and sudo cd ... can't work either, since cd is a shell builtin, not a program sudo can exec. Running both as one privileged command sidesteps both problems: root bypasses the permission check, and svc.sh install needs root anyway to write the systemd unit. 
sudo bash -c 'cd /home/gha-runner/actions-runner && ./svc.sh install gha-runner'

The gha-runner argument tells the installer to run the service as that user (not root) — this generates /etc/systemd/system/actions.runner.Linkify-Solutions-Inc-kubernetes-streaming.kubernetes-server.service.

06

Add the CPU constraint

on the box
Why — Kafka's bursty log-segment writes and a live ffmpeg encode are both real CPU consumers on this box (empirically ~2.3 cores per live stream, see SPEC.md). An unconstrained docker build running concurrently could win the CPU scheduler fight against a live stream mid-encode. Nice= lowers its traditional scheduling priority; CPUWeight= does the equivalent under cgroup v2 (what modern systemd uses) — both make the runner yield CPU under contention rather than compete evenly. 
sudo systemctl edit actions.runner.Linkify-Solutions-Inc-kubernetes-streaming.kubernetes-server.service

this opens an editor for an override file — paste:

[Service]
Nice=10
CPUWeight=50

Save and exit (in nano: Ctrl+O, Enter, Ctrl+X).

07

Start it and confirm it's alive

on the box 
sudo systemctl start actions.runner.Linkify-Solutions-Inc-kubernetes-streaming.kubernetes-server.service
sudo systemctl status actions.runner.Linkify-Solutions-Inc-kubernetes-streaming.kubernetes-server.service

You want active (running). Then check GitHub sees it: 

gh api repos/Linkify-Solutions-Inc/kubernetes-streaming/actions/runners --jq '.runners[].name'
Confirms — should print kubernetes-server.

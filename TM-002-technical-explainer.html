Chapter 1 — The ideas underneath everything

1-1.Containers, images, pods. A container is a normal Linux process wearing blinders: kernel namespaces limit what it can see (its own filesystem, network, process list) and cgroups limit what it can use (CPU, memory). It is not a virtual machine — there is no second kernel — which is why one starts in milliseconds. An image is the frozen filesystem a container starts from, built once by a Dockerfile, layered so that shipping a one-line code change re-transfers kilobytes, not gigabytes. Our five services each build to an image pushed to GitHub's registry (GHCR); the transcode image is the heavyweight (~1.5 GB) because it carries ffmpeg. A pod is Kubernetes' unit of scheduling: one or more containers that share a network identity and fate. Nearly every pod here holds one container; the Kafka broker pod holds sidecars.

1-2.Kubernetes in one paragraph. You hand Kubernetes a desired state — "two replicas of web, version X, 256 MiB each" — and controllers work in loops to make reality match, forever. A node dies; its pods reappear elsewhere. This reconciliation model is the single most important idea in the platform: nothing in this system is ever "installed", things are declared, and machinery converges. Every defect chapter 5 dissects is at bottom a declaration the machinery could not satisfy — and every fix is a better declaration, never a manual poke at a live object.

1-3.Infrastructure as code. The same philosophy applied below Kubernetes: infra/eks/cluster.yaml declares the VPC, control plane, node group, and add-ons; eksctl compiles it to CloudFormation stacks (AWS's own reconciliation engine). The payoff you experienced directly in TM-001: the entire environment was destroyed and rebuilt from the same files. The discipline it demands: if you click something into existence in the console, it is invisible to the files, survives no rebuild, and is a lie waiting to be discovered. The reference build enforces this so hard that even the teardown is a version-controlled script.

Design choice — why eksctl + CLI, not Terraform or Pulumi

Three tools share the IaC job here: eksctl→CloudFormation for the cluster (declarative, and stateless — CloudFormation is the state, so there is no state-backend bootstrap problem), GitOps for everything inside Kubernetes, and plain AWS CLI — documented, discovery-based, scripted for teardown — for the data layer. Terraform would have unified the AWS side: one apply, one destroy, and a dependency graph that automatically prevents deletion-ordering bugs like case 19. It was not used because it adds a second declarative language, a state backend, and a layer of abstraction between the learner and the actual API calls — the wrong trade for a one-cluster teaching platform, and the right first epic if this ever goes to production. Pulumi is the same model with a general-purpose language; strictly more machinery than this system needs.

1-4.GitOps. CI/CD's traditional shape is push-based: a pipeline holds cluster credentials and runs kubectl apply. GitOps inverts it: an agent inside the cluster (ArgoCD) watches the git repository and pulls reality toward it. Three consequences run through everything you did in TM-001: (1) git is the sole entry point — the build's only hand-applied manifest is the one that installs the watcher itself; (2) the current system state is reviewable as a diff and revertible as a commit; (3) drift heals itself — a manual change to a live object gets overwritten on the next sync, which is a feature, and which is also why TM-001's teardown begins by disarming that self-healing. The "app-of-apps" pattern layers this: one root Application whose only job is to sync a directory of other Application manifests.

1-5.CI and CD are different machines here. CI (GitHub Actions, .github/workflows/ci.yml) proves and packages: tests run, images build, tags land in the registry, and a one-line kustomize edit records the new tag in git. CD is ArgoCD noticing that commit. The pipeline never touches the cluster; the cluster never touches the pipeline. Their only shared surface is the repository — which is precisely what makes the system auditable: everything that ever happened is a commit.

1-6.Autoscaling, two-layered. Workload autoscaling (KEDA) answers "how many copies of the work should exist?" by watching queue pressure — Kafka consumer lag — and cutting Kubernetes Jobs to match, down to zero. Infrastructure autoscaling (Karpenter) answers "how many machines should exist?" by watching for pods that fit nowhere and buying/returning EC2 capacity in response. Neither knows the other exists; they compose through the scheduler. Chapter 6 walks the real measured timeline of both layers firing.

1-7.Secrets, without secrets in git. The chain is: AWS Secrets Manager holds the value → External Secrets Operator (ESO) reads it and materializes a Kubernetes Secret → the pod mounts it. Authentication uses EKS Pod Identity: AWS binds an IAM role to a (cluster, namespace, service-account) triple, and the SDK inside the pod picks up short-lived credentials automatically. Zero keys on disk, zero passwords in git, rotation without redeploys. The older mechanism (IRSA — role ARN annotated on the service account, trust via the cluster's OIDC provider) survives where controllers still require it: the load balancer controller and Karpenter. Knowing which of the two you are wiring is a recurring exam question in real life.

Chapter 2 — System architecture & the life of a stream

2-1.The cast. Five in-house services (all Python/FastAPI): web (UI: create streamers, upload videos, watch), upload-api (the platform's API and S3 gatekeeper), ingest-webhook (MediaMTX's brain: authenticates stream keys, emits lifecycle events), transcode-worker (ffmpeg wrapped in a Kafka consumer), analytics-worker (folds events into Postgres). Around them, infrastructure: MediaMTX (RTMP ingest server), Kafka (the event backbone, run by the Strimzi operator), Postgres (RDS), S3 + CloudFront (media storage and delivery), and the platform operators (ArgoCD, ESO, KEDA, Karpenter, load balancer controller, Prometheus/Grafana).

2-2.Life of a live stream — the exact path your Chapter 11 test exercised, worth internalizing because every ops question ("why is X down?") is a question about one arrow of it:

  1. OBS/ffmpeg publishes RTMP to the NLB → MediaMTX. MediaMTX does not decide anything itself: it calls ingest-webhook /hooks/auth with the stream key.
  2. ingest-webhook checks the key against Postgres. Valid → MediaMTX accepts; a row's UUID becomes the stream's public identity (the secret key never appears in any URL).
  3. On publish, ingest-webhook writes one message to Kafka topic stream.start.requests and lifecycle events to stream.lifecycle.
  4. KEDA, polling that topic's consumer lag, sees 1 pending message and creates one transcode-live Job (ceiling: 8 concurrent, matching the topic's partitions).
  5. The Job's pod demands a transcode-tainted node; none exists; Karpenter launches one (c6a.xlarge, 46 s in the reference run).
  6. The worker consumes the message, pulls the live RTMP feed from MediaMTX, and ffmpeg emits an adaptive ladder (1080p/720p/480p) of 4-second HLS segments straight to s3://…/hls/live/<uuid>/ — via the S3 gateway endpoint, dodging NAT fees.
  7. Viewers fetch master.m3u8 through CloudFront; playlists are never cached (they change every segment), segments are cached hard (they never change).
  8. Stream ends → unpublish hook → worker exits → Job completes → ~2 min later Karpenter deletes the now-idle node. Meanwhile analytics-worker has been folding transcode.status/viewer.analytics events into Postgres.

2-3.Why Kafka sits in the middle. The webhook could have started transcoders directly — an HTTP call. Then a transcoder crash loses the stream, a burst of streams overwhelms whatever receives the calls, and adding a second consumer (analytics) means touching the webhook. The queue decouples all three axes: durability (the message outlives any consumer crash), backpressure (8 partitions are the concurrency ceiling — the queue absorbs the ninth stream until a slot frees), and fan-out (analytics subscribes without anyone's permission). The price is operational: Kafka was, by a wide margin, the most defect-dense component of the build (five of the eighteen case studies).

2-4.Network posture. Everything computes in private subnets; the internet reaches exactly three front doors (NLB for RTMP, ALB for HTTPS, CloudFront for media), and the pods reach out through one NAT gateway — except S3 traffic, which the free gateway endpoint keeps off the meter. The Postgres security group admits port 5432 from the cluster's security group only; there is no bastion, no SSH, no public database, and kubectl reaches the API server over TLS with IAM-authenticated, MFA-backed, 8-hour credentials.

Chapter 4 — The YAML, file by file

4-1. infra/eks/cluster.yaml — the ground floor

One declaration, two CloudFormation stacks. Its stanzas, and why each is the way it is:

StanzaWhat it does, and the decision inside it

availabilityZonesPinned to two AZs. Left unpinned, eksctl picks AZs at random per run — which desynced from the nodegroup's AZ list and killed the first build (case study #1). Pinning makes the file deterministic.
autoModeConfig: enabled: falseFuture eksctl versions flip clusters to "Auto Mode" by default, which stops honoring the nodegroup/add-on stanzas. Pinned so a newer eksctl builds the same cluster.
accessConfigauthenticationMode: API: cluster admission is controlled by auditable EKS access-entry API objects, not the legacy in-cluster ConfigMap that generations of operators have locked themselves out with. 4-2. k8s/bootstrap/root-app.yaml — the ignition key

An Application pointing at k8s/argocd/apps/ on GitHub master. Its resources-finalizer makes deletion cascade (without it, deleting root orphans everything). Its comment carries the whole GitOps contract: "the one and only manifest a human ever applies with kubectl. From here on, everything is a git commit." Note it reads GitHub, not your laptop — an unpushed commit does not exist (TM-001 repeats this at every substitution for this reason).

4-3. k8s/argocd/apps/ — the app-of-apps

Filename prefixes mirror the sync-wave annotations inside: platform operators and storage at wave 0, secrets and Karpenter pools at 10, Kafka at 20, schema migration at 25, our services at 30, MediaMTX at 40. Waves are ArgoCD's dependency mechanism: wave N+1 does not apply until wave N is healthy. Two hard-won rules live in this directory's comments: the kustomization.yaml means a file not listed in it does not exist, no matter that it sits in the directory (case #9); and 40-mediamtx.yaml has an empty syncPolicy — deliberately manual, because syncing it is the act that creates a billable NLB, and money-creating actions get a human finger on them.

4-7. services/, the Dockerfiles, and the compose mirror

Each service ships a near-identical Dockerfile: a slim Python base image; requirements.txt copied and installed before the source code (so the expensive dependency layer caches across code-only rebuilds — the layering idea from §1-1 doing real work); a non-root user (the restricted PodSecurity standard in §4-6 assumes it); and a plain uvicorn entrypoint. The transcode image alone adds ffmpeg, which is why it weighs ~1.5 GB and dominates cold-start (§6-2).

docker-compose.yml is the whole platform shrunk onto one laptop: the five services, one Postgres, one Kafka, one MediaMTX — same images, same env-var names, same postgres/migrations/ schema files the cluster's db-migrate Job replays. That parity is a design decision, not a convenience: a bug reproduced in compose is the same bug the cluster has, minus every AWS variable. When something misbehaves in EKS, "does compose do it too?" is the cheapest bisection you own — it splits the universe into our code versus the platform around it in thirty seconds.

Chapter 5 — Eighteen defects: case studies

Everything below actually happened, in this order, in one build. None are exotic; all are the daily texture of platform work. Each entry ends with the transferable lesson — the part worth memorizing.

Case 1 — The random availability zones

Symptom: nodegroup creation failed: "could not find private subnets for zones [us-east-1a us-east-1b]" — yet the config looked reasonable. Cause: cluster-level AZs were unpinned, so eksctl chose two at random (1f, 1a); the nodegroup stanza independently pinned (1a, 1b). Two sections of one file disagreed about geography. Fix: pin availabilityZones once at cluster level; subordinate lists must be subsets. Lesson: anything a tool "helpfully" chooses for you is a different choice every run. Declarative means fully declared.

Case 2 — The empty tag

Symptom: CloudFormation rejected the nodegroup: "tags.6.member.value… length greater than or equal to 1". Cause: karpenter.sh/discovery: "" on the nodegroup — an empty-valued tag, illegal in the CreateStack API, and semantically useless anyway (Karpenter only manages nodes it created; a managed nodegroup needs no opt-out). Fix: delete the tag. Lesson: when a mechanism is "cleverly" disabled by an empty value, first ask whether the mechanism applied at all.

Case 3 — The relative path

Symptom: "no such file or directory: infra/eks/cluster.yaml". Cause: command run from ~. Fix/Lesson: repo-relative paths mean repo-root working directory. Trivial — and the most common failure new operators hit, which is why TM-001 states it in Chapter 1.

Case 4 — Seventeen pods per node

Symptom: app pods Pending: "0/2 nodes are available: 2 Too many pods" — with CPU and memory half idle. Cause: on the default VPC-CNI addressing mode, pod capacity is an IP arithmetic limit — 17 on t3.medium — and the platform layer alone (ArgoCD, monitoring, ESO, KEDA, operators, kube-system) consumes two nodes of slots before any app runs. Karpenter cannot help: its pools are transcode-tainted on purpose. Fix: third node. Lesson: nodes have three capacities — CPU, memory, pod slots — and the invisible third one binds first on small instances. (Prefix delegation raises it, at the cost of a nodegroup roll.)

Case 5 — The file nothing synced

Symptom: PVCs Pending: "storageclass gp3 not found" — yet storageclass-gp3.yaml sat right there in the repo. Cause: it sat at a path no Application's source.path covered. GitOps has no "apply this too" — a manifest outside every Application is simply not part of the cluster. Fix: move it under a new wave-0 storage Application. Lesson: in GitOps, existence = being inside some Application's path. An orphaned manifest is documentation cosplaying as configuration.

Case 6 — The Kafka version the operator refused

Symptom: Kafka CR NotReady: UnsupportedKafkaVersionException: 3.9.0. Supported: [4.0.0 … 4.1.1]. Cause: the CR's version pin predated the operator's pin; Strimzi ships specific broker images per release and 0.49 had dropped 3.9. Fix: 4.1.1, and drop the metadataVersion pin (fresh cluster → operator defaults it correctly). Lesson: pins that reference each other move together; the file now carries the command that lists what the operator actually ships.

Case 7 — The lock held against its own fix

Symptom: case 6's fix was pushed… and the live CR stayed at 3.9.0. No error anywhere. Cause: the kafka Application's first sync was still "Running": its PostSync hook made ArgoCD wait for all resources healthy; the topics could never be healthy while the CR was rejected; and ArgoCD will not start a new sync while one runs. The broken state held the lock against the commit that would fix it. Fix: terminate the operation (status.operationState.phase: Terminating); auto-sync then applied the fix. Lesson: when a pushed fix "isn't taking effect" under ArgoCD, read .status.operationState before pushing harder. It happened again two hours later (case 14) — this pattern is worth over-learning.

Case 8 — The ConfigMap made of comments

Symptom: Strimzi: "Failed to parse metrics configuration… No content to map" — and the whole Kafka reconcile failed, not just metrics. Cause: the metrics ConfigMap was a placeholder whose data was YAML comments only — syntactically present, semantically empty. Fix: the verbatim example ConfigMap from the pinned Strimzi release. Lesson: a placeholder that parses is worse than a missing file; and operators may fail the whole resource on a "peripheral" config error.

Case 9 — The kustomization that ignored a file

Symptom: case 5's fix (a new Application file) changed nothing; root reported Synced. Cause: k8s/argocd/apps/ contains a kustomization.yaml, so ArgoCD renders the directory through kustomize — and kustomize includes only what resources: lists. The new file was invisible, and "Synced" was truthful about the wrong question. Fix: list it. Lesson: file in that directory ⇔ line in that list, always both — and green statuses answer precisely the question asked, not the one you meant.

Case 10 — Two gigabytes with nowhere to sit

Symptom: broker pod Pending: "3 Insufficient memory" plus Karpenter's "did not tolerate taint". Cause: the broker requests a contiguous 2 GiB; every t3.medium with platform pods aboard had less free; the autoscaler's pools are deliberately not for stateful brokers. Fix: fourth node (the declared maxSize). Lesson: scheduling is bin-packing; a big request needs a big hole, not big aggregate capacity. The config comment now says: at a hypothetical 5th node, change instance size instead (2 × t3.large = same price as 4 × t3.medium, double the holes).

Case 11 — The migration that couldn't read its own SQL

Symptom: db-migrate Application stuck sync-status Unknown; render error citing ../../../../postgres/migrations/…. Cause: kustomize's load restrictor (a security default) forbids reading outside the kustomization root; sharing one schema directory between compose and cluster requires the repo-server-wide option. Fix: kustomize.buildOptions: --load-restrictor LoadRestrictionsNone in the ArgoCD Helm values — where it survives upgrades. TM-001 bakes it into the install command. Lesson: "a global setting" in a design note is a task, not a fact — someone must set it somewhere specific.

Case 12 — The Job that ran with zero pods

Symptom: db-migrate "Running" for six minutes; kubectl get pods: none; logs: none. Cause: the namespace enforces restricted PodSecurity; the Job's container lacked seccompProfile; pods were rejected at admission — before existing, before logging. The only evidence: kubectl describe job → FailedCreate events. Fix: one securityContext field. Lesson: the least discoverable failure shape in Kubernetes. When a controller seems busy but produces nothing, describe the controller's object, not its (nonexistent) children.

Case 13 — The placeholder that lived twice (and the env var that lived zero times)

Symptom: upload-api never Ready (S3 check: Invalid bucket name "…<accountid>"); ingest-webhook crashlooping (missing required environment variables). Cause (a): the bucket-name placeholder existed in two files; the fix landed in the redundant one. Cause (b): the Deployment wires env vars one-by-one and one of the app's three require()s had no line. Fix: real value in the file that matters; the missing configMapKeyRef. Lesson: grep -rn "<placeholder>" the whole tree before declaring a substitution done; and explicit env wiring is a contract — the app names all missing vars at once precisely so you fix them in one pass, use that.

Case 14 — The Ingress that held every rollout hostage

Symptom: config fixes queued for an hour; the streaming app's operation "Running — waiting for healthy state of Ingress/streaming". Cause: the Ingress cannot be healthy until an ACM certificate validates — an event outside the cluster (DNS delegation pending) — and it sat in an early sync wave with resources sequenced after it. Case 7's lock mechanism, external edition. Fix: real cert ARN + move the Ingress to the last wave, where nothing waits on it. Lesson: resources whose health depends on the outside world go in the final wave. Order by dependency, not by importance.

Case 15 — The health check the policy didn't cover

Symptom: upload-api readyz: S3 403 on HeadBucket — with correct bucket name and a policy that "obviously" allowed its work. Cause: least-privilege scoping gave ListBucket only under a raw/* prefix condition; HeadBucket performs an unprefixed ListBucket check. The app's probe needed more than the app's work. Fix: unconditioned ListBucket (object writes stay prefix-scoped). Lesson: test least-privilege against the whole process — health checks included — not against the happy path.

Case 16 — The success that did nothing

Symptom: a five-minute live stream published flawlessly. No transcoder ever started. Zero errors in any log. Cause: the consumer groups had never been bootstrapped (their hook died in case 7's terminations); KEDA cannot compute lag for a group with no committed offsets, and scaleToZeroOnInvalidOffset: true converts "cannot compute" into "no work". Every component was individually correct. Fix: re-run the hook; verify groups exist. Lesson: the worst failures are compositions of correct parts. For any scale-from-zero trigger, verify the trigger's own prerequisites — TM-001 makes the group check a mandatory pre-stream checkpoint because this failure will never announce itself.

Case 17 — The image tag that never existed

Symptom: the bootstrap hook, once finally running, sat in ImagePullBackOff for 40 minutes: quay.io/strimzi/kafka:0.49.0-kafka-3.9.0 not found. Cause: the job's image tag encodes both pins (operator-kafka); case 6's fix updated one file and not this one. Fix: align; comment now warns the tag moves with both pins. Lesson: when you bump a version, grep for it — pins hide in job images, CI files, and docs, not just the obvious CR.

Case 18 — Teardown is a dependency graph too

Four sub-lessons from unwinding the platform, now encoded as the ordered procedure in scripts/teardown.sh: (a) a live root app resurrects deleted children — disarm selfHeal first; (b) apps that own load balancers die first, while the controller that can release them still lives — or AWS keeps billing for orphans; (c) CR consumers before operators — an operator deleted before its CRs leaves finalizers no one can service and namespaces wedged Terminating; (d) aggregated APIServices outlive their backends and poison cluster-wide discovery — the dead registration must be deleted by hand. Lesson: deletion order is creation order reversed, including the implicit edges (controllers, finalizers, API registrations) that creation got for free.

Chapter 6 — Autoscaling economics

6-1.The measured timeline. One live stream, real clock, 2026-08-11 (this is the reference for TM-001's lab):

6-2.The cold-start ledger. Those 77 seconds decompose as ~35 s KEDA polling latency + 24 s machine + ~18 s image pull, ffmpeg spin-up, and the first 4-second segment. Two facts sharpen the trade: only the first viewer of a just-started stream experiences it, and the first ~77 s of the broadcast are simply absent from the HLS output (the worker joins a live feed). The alternative — one warm transcode node always on — costs c6a.xlarge × 730 h ≈ $112/month. At ~$0.03 marginal cost per cold start, warm capacity breaks even only past ~3,700 stream-starts a month. For a learning platform the answer is obvious; for a business, this one table is the pricing meeting.

6-3.Why two autoscalers and not one. KEDA reasons about work (queue depth), Karpenter about capacity (unschedulable pods). Collapsing them means either the queue-watcher must understand EC2 or the machine-buyer must understand Kafka. Composed through the scheduler, each stays simple, and the coupling is exactly one signal: a Pending pod. Notice also what deliberately does not autoscale: the system nodegroup (the platform floor is a fixed cost) and the Kafka broker (stateful, do-not-disrupt; scaling data systems is a decision, not a reflex).

Chapter 7 — CI/CD: how code becomes a running platform

7-1.CI (.github/workflows/ci.yml). On every push: lint + unit tests for the services that have them, then — only for services whose files actually changed — a Docker build pushed to GHCR tagged both latest and sha-<commit>. Path-filtering matters: an infra-only commit builds zero images and finishes in under a minute, which you saw in the reference build's history.

7-2.The handoff commit. CI's last act on a service change is kustomize edit set image …:sha-abc1234 inside k8s/apps/overlays/prod — a one-line, machine-writable, human-reviewable git commit. That commit is the entire interface between CI and CD. ArgoCD notices it like any other commit and rolls the deployment. Rollback is git revert. Deployment history is git log. No pipeline holds cluster credentials; nothing can deploy that isn't in git.

7-3.Registry visibility. The five images are public on GHCR — chosen during the reference build over maintaining pull-secret machinery (a classic security-vs-friction call; the code was public anyway). Consequence worth knowing: the cluster needs zero registry credentials, and one whole class of ImagePullBackOff is structurally impossible.

7-4.The ceiling-sync guard. scripts/check_ceiling_sync.sh runs in CI and fails the build if MAX_CONCURRENT_LIVE_STREAMS (app config), the transcode-live ScaledJob ceiling, and the topic partition count drift apart. Three files must agree for the backpressure story in §2-3 to hold; CI is where that agreement is enforced, because humans forget and reviews miss it. This tiny script is the purest expression of CI's real job: make the repository unable to lie to itself.

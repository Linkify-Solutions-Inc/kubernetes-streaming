Most Kubernetes explanations start with a list of components — apiserver, scheduler, kubelet — and never say what holds them together. That gets you a vocabulary but not a mental model, and it's why Kubernetes feels arbitrary for a long time before it suddenly doesn't.

This guide goes the other way. There is exactly one idea at the centre of Kubernetes, and every component is a consequence of it. Once that idea is clear, the rest stops being a list to memorise and becomes something you can reason about — including the failures.

01

The core idea: declare the destination, not the route

Almost every system administration tool before Kubernetes was imperative. You issued commands: start this process, copy that file, open this port. The tool did what you said, in order, once. If it half-finished, you owned the mess. If something drifted afterwards, nobody noticed.

Kubernetes is declarative. You never tell it to do anything. You write down a description of the world you want, hand it over, and the system continuously works to make reality match. "Three replicas of this image exist" is a statement about how things should be, not an instruction to start three containers.

The whole system in one sentence — Kubernetes stores your desired state, observes the actual state, and runs a never-ending loop that tries to close the gap between them.

The reconciliation loop

That loop is the fundamental unit of the system. It looks like this, and it never terminates: 

for {
    desired  := readFromAPI()      // what the user asked for
    actual   := observeWorld()     // what's really running
    if diff := compare(desired, actual); diff != nil {
        act(diff)                  // take one step to close the gap
    }
}

A piece of code that runs this loop is called a controller. Kubernetes is, essentially, several dozen controllers running concurrently, each watching a small slice of the world and each caring about exactly one kind of gap.

Level-triggered, not edge-triggered

This distinction sounds academic and is actually the single most important design decision in the system.

Edge-triggeredLevel-triggered
Reacts to Events — "a pod died" State — "there are 2 pods, I want 3"
Miss an event Permanently wrong Next loop fixes it
Restart the controller Lost all pending work Re-observes, carries on
Duplicate event Acts twice — bug Second pass sees no gap, does nothing

Kubernetes controllers are level-triggered. They do use a watch stream for efficiency — reacting immediately beats polling — but the watch is only a hint to look sooner. The decision is always made by comparing full current state against full desired state. Every controller also re-syncs on a timer regardless of events.

Why this makes everything else possible — it is what makes the system self-healing rather than merely automated. A controller can crash mid-action, miss every event while it was down, come back with no memory of what it was doing, and still converge — because it never needed the history, only the present. This is also why kubectl apply is safe to run a hundred times.
The consequence people trip on — nothing in Kubernetes is transactional or immediate. Applying a manifest returns as soon as the record is stored, not when the world matches it. Everything after that is eventual. When a pod isn't running yet, the honest question is almost never "did the command fail?" but "which controller is stuck, and what does it think is wrong?"
02

Objects: spec, status, and one door

If controllers compare desired against actual, both have to be written down somewhere. That is what a Kubernetes object is, and it's why nearly every object has the same two-part shape: 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: streaming
  labels: { app: web }
spec:                      # DESIRED — written by you
  replicas: 3
status:                    # ACTUAL — written by a controller
  replicas: 3
  readyReplicas: 2
  unavailableReplicas: 1
The most useful habit in Kubernetes — when something is wrong, read status, not spec. spec is just your own wish reflected back at you; it is true by construction and tells you nothing. status is the system reporting what it actually managed to achieve, and it is where the answer lives. This is what kubectl describe is really for.

Identity: names, namespaces, labels

  • Name — unique per kind, per namespace. Renaming is not a thing; you delete and create.
  • Namespace — a scope for names, and the unit that RBAC, quotas and NetworkPolicy attach to. Not a security boundary on its own: pods in different namespaces can reach each other freely unless a NetworkPolicy says otherwise.
  • Labels — arbitrary key/value pairs that are queryable. This is how objects find each other.
  • Annotations — arbitrary key/value pairs that are not queryable. For data meant for tools and humans, not selectors.
Labels are the joining mechanism — there are no foreign keys and no direct references in Kubernetes. A Service doesn't hold a list of its pods; it holds a label selector, and membership is computed continuously. That's why adding a label to a running pod can silently put it into production traffic, and why a one-character typo in a selector produces a Service with zero endpoints and no error message anywhere.

Ownership and cascading deletion

Objects created by controllers carry an ownerReferences field pointing at their parent. This forms a tree — Deployment owns ReplicaSet owns Pod — and the garbage collector uses it: delete the Deployment and everything beneath it is removed, because each child records who it belongs to. This is also how an orphaned ReplicaSet with no owner keeps running forever after a botched delete.

Finalizers

A finalizer is a string on an object that blocks its deletion. When you delete such an object, the API server only sets deletionTimestamp; the object stays until the controller responsible for that finalizer does its cleanup and removes the string.

The classic hang — a namespace stuck Terminating forever is almost always a finalizer whose controller is gone — frequently a deleted operator that left CRs behind. Nothing is broken in Kubernetes; a promise is simply outstanding and nobody is left to keep it.

Everything goes through the API server

No component reads or writes etcd directly except the API server. The scheduler doesn't. The kubelet doesn't. Controllers don't. They all speak HTTP to the same endpoint you do with kubectl — with the same authentication, the same RBAC, the same admission checks and the same audit log.

Why this matters — it means there are no privileged side channels. Every state change in the cluster is a normal API request, which is what makes the whole system uniformly observable, uniformly securable, and extensible by anyone who can write an HTTP client. Your controller is not a second-class citizen next to the built-in ones — it is literally the same kind of thing.

Watches and optimistic concurrency

Every object carries a resourceVersion. Clients WATCH from a version and receive a stream of changes since then, rather than polling. On write, a client can send the version it read; if someone else has modified the object in the meantime, the write is rejected with a conflict and the controller retries from fresh state.

No locks, no leases on the data. Concurrent controllers just retry — which works precisely because they are level-triggered and losing a round costs nothing.

etcd

A distributed key-value store using the Raft consensus algorithm. It is the only stateful component in the entire system — everything else can be killed and restarted with no data loss, because everything else keeps its state here.

Raft needs a quorum, which is why control-plane node counts are odd (3, 5) — and why etcd is unusually sensitive to disk latency. A slow disk causes missed heartbeats, which causes leader elections, which stalls every write in the cluster. "The cluster feels slow" is very often an etcd fsync problem.

kube-apiserver

A REST server in front of etcd, and the only component that talks to it. Each request runs a fixed pipeline:

  1. Authentication — who is this? (client cert, bearer token, ServiceAccount token)
  2. Authorization — may they do this? (RBAC)
  3. Mutating admission — modify the object before storing
  4. Schema validation — is it well-formed?
  5. Validating admission — accept or reject outright
  6. Persist to etcd

It is stateless, so it scales horizontally — you can run several behind a load balancer.

kube-scheduler

One loop, one job: watch for pods with an empty spec.nodeName, decide which node each should run on, and write that decision back. It never starts a container — it only fills in a field. Covered in depth in §6.

kube-controller-manager

A single binary running roughly thirty independent control loops in goroutines. The Deployment controller, ReplicaSet controller, Job controller, Node controller, EndpointSlice controller, ServiceAccount controller, garbage collector and others all live here. They are bundled for operational convenience; conceptually each is separate and none knows about the others.

kubelet

The agent on each node, and the component that actually causes containers to exist. Its loop:

  • Watch the API server for pods where spec.nodeName == thisNode
  • For each, ensure the containers described are running, via the CRI (Container Runtime Interface) — a gRPC API the runtime implements
  • Call the CNI plugin to give the pod a network namespace and an IP
  • Mount volumes, inject ConfigMaps and Secrets
  • Run probes; restart containers per restartPolicy
  • Report observed state back into the pod's status
Note the direction — the kubelet pulls from the API server. The control plane never connects to it to push work. That's why a node behind NAT with no inbound connectivity works fine, and why a node losing contact keeps running its existing pods quite happily — it simply stops hearing about changes.

kube-proxy

Watches Services and EndpointSlices and programs the kernel so that traffic to a Service's virtual IP reaches a real pod. In the default iptables mode it writes NAT rules; IPVS and nftables modes exist for larger clusters. It handles no packets itself — it only configures the kernel, which does all the work. See §9.

04

Pods: why the atom isn't a container

Kubernetes never schedules a container. The smallest deployable unit is a Pod: one or more containers that share a network namespace, IPC namespace, and any volumes you define.

What sharing actually means

  • All containers in a pod share one IP address and one port space. They reach each other on localhost, and two of them cannot both bind port 8080.
  • The IP belongs to the pod, not to any container. Containers can restart and the address is unchanged.
  • Volumes are declared at pod level and mounted into whichever containers need them.
The pause container — the namespace has to be owned by something that outlives individual containers, or a crash-restart would drop the IP. So the kubelet starts a tiny near-empty container first — the pause container — whose only job is to hold the namespaces open. Every other container in the pod joins its namespaces. It's why every node has a pause image, and why you see one extra container per pod at the runtime level that never appears in your YAML.

When to put two containers in one pod

The test is not "are these related?" — it's "must these always be scheduled onto the same machine and scale as a single unit?" If the answer is no, they are two pods. A web app and its database are related and belong in separate pods. A web server and a log shipper reading its files through a shared volume genuinely cannot be separated — that's a sidecar.

Init containers

Run to completion, in declared order, before any app container starts. Each must exit 0 or the pod restarts. Useful for waiting on a dependency, running a schema migration, or fetching config — and because they're separate images, they can carry tools you don't want in the runtime image.

Phases and conditions

PhaseMeaning
PendingAccepted, but not all containers running. Either unscheduled, or scheduled and still pulling images.
RunningBound to a node, all containers created, at least one running.
SucceededAll containers exited 0 and won't restart.
FailedAll terminated, at least one non-zero.
UnknownThe node stopped reporting.

Phase is a coarse summary. The detail is in status.conditions — PodScheduled, Initialized, ContainersReady, Ready — which is where you find out which step is stuck.

The three probes

These are constantly confused, and they do completely different things.

ProbeOn failureAnswers
liveness Kills and restarts the container "Is this wedged and beyond recovery?"
readiness Removes it from Service endpoints. Container keeps running "Should it receive traffic right now?"
startup Kills it — but suspends the other two until it first passes "Has slow initialisation finished?"
The classic outage — pointing a liveness probe at an endpoint that depends on a database. The database has a blip, every replica's liveness probe fails at once, Kubernetes restarts the entire fleet simultaneously, and now you have a cold-start stampede on top of a database problem. Liveness should test only whether the process itself is healthy. Dependency checks belong in readiness, where failure removes traffic instead of destroying the process.

Termination

Deletion is not instant. The sequence is: the pod is marked terminating and simultaneously removed from Service endpoints; preStop hooks run; SIGTERM is sent; Kubernetes waits up to terminationGracePeriodSeconds (default 30); then SIGKILL.

Endpoint removal and SIGTERM race — they propagate through different paths — so a container that exits immediately on SIGTERM can still drop in-flight requests. Handling SIGTERM by finishing current work before exiting is the difference between rolling updates that are invisible and rolling updates that produce a spike of 502s.

05

Controllers: the workload objects

Bare pods are rarely written by hand — nothing recreates them if the node dies. Instead you declare a higher-level object and a controller manages the pods beneath it.

Deployment → ReplicaSet → Pod

The most common chain, and it's genuinely two controllers stacked:

Deployment controller — owns rollout strategy
Deploymentreplicas: 3, image: v2
↓ creates a new ReplicaSet per pod-template change
ReplicaSet controller — owns "keep N alive"
ReplicaSet v1scaled to 0
ReplicaSet v2scaled to 3
↓ creates/deletes to match its own count
Pods
pod-v2-aRunning
pod-v2-bRunning
pod-v2-cRunning

A ReplicaSet only knows how to hold a count steady. A Deployment adds versioning: change the pod template and it creates a second ReplicaSet, then shifts replicas from old to new, governed by maxSurge (how many extra may exist during the rollout) and maxUnavailable (how many may be missing).

Old ReplicaSets are kept at zero replicas rather than deleted — that is what kubectl rollout undo uses. A rollback is just scaling a previous ReplicaSet back up.

StatefulSet

For workloads where the replicas are not interchangeable — databases, message brokers, anything with a cluster identity. It provides four guarantees a Deployment does not:

  • Stable ordinal names — kafka-0, kafka-1, not random suffixes. A replacement for kafka-0 is also called kafka-0.
  • Stable network identity — each pod gets a resolvable DNS name via a headless Service, so peers can address each other individually.
  • Stable storage — volumeClaimTemplates creates one PVC per pod, and a restarted kafka-0 reattaches to the same volume with the same data.
  • Ordered operations — pod N isn't created until N-1 is Ready; updates roll in reverse ordinal order.
PVCs outlive the StatefulSet — scaling down, or deleting the StatefulSet, does not delete the PersistentVolumeClaims by default. This is deliberate — accidental deletion of a database would otherwise be one command away — but it surprises people who scale down to "clean up" and find the storage still there, still billed, and still attached when they scale back up.

DaemonSet

One pod per node, automatically, including on nodes that join later. For things that are properties of a machine rather than of an application: CNI agents, log collectors, node exporters, storage drivers. DaemonSets usually carry tolerations so they run even on tainted nodes — a log collector that skips your control-plane nodes isn't much of a log collector.

Job and CronJob

A Job runs pods until a specified number complete successfully, rather than keeping them running forever. completions sets how many successes are needed, parallelism how many may run at once, backoffLimit how many failures before giving up. A CronJob is a controller that creates Jobs on a schedule.

Why this matters for run-to-completion work — the Job model demands a fundamentally different program shape than a Deployment. A Deployment container is a daemon: start, loop forever, never exit — and exiting is a failure. A Job container must do one unit of work and then exit zero — and not exiting is the failure. A long-running consumer loop cannot be turned into a Job by changing the manifest; the program has to be restructured to take its input, act once, and terminate.
06

Scheduling: how a pod picks a node

The scheduler watches for pods with no spec.nodeName. For each, it runs two phases.

Phase 1 — Filtering

Reduce all nodes to those that could host the pod. A node is eliminated if any check fails:

  • Insufficient allocatable CPU/memory for the pod's requests
  • Node doesn't match nodeSelector or required affinity
  • Node has a taint the pod doesn't tolerate
  • Required ports already taken (for hostPort)
  • Required volume can't be attached there

No survivors means the pod stays Pending, with the reason recorded in its events. This is the single most common thing to look at when a pod won't start.

Phase 2 — Scoring

Rank the survivors and pick the best. Scoring favours spreading pods of the same Service across nodes, balanced resource utilisation, and nodes that already have the image cached. Then the scheduler issues a Binding — an API write that sets nodeName. That write is the entire act of scheduling. The kubelet on that node notices and takes over.

Taints and tolerations — a repulsion mechanism

A taint on a node repels pods. A toleration on a pod lets it ignore a specific taint. Three effects: NoSchedule (don't place new pods), PreferNoSchedule (avoid if you can), NoExecute (also evict pods already running there).

Direction is the thing to keep straight — taints are the node saying "stay away unless you're special"; affinity is the pod saying "I want to be near X". Taints exclude by default and require opt-in; affinity attracts. A dedicated GPU node needs a taint — otherwise ordinary pods land on it and consume the machine you set aside.

Affinity and anti-affinity

  • Node affinity — place me on nodes with these labels.
  • Pod affinity — place me near pods matching this selector (co-locate with a cache).
  • Pod anti-affinity — keep me away from them. This is how you stop all three replicas of a database landing on one node and losing everything together.

Each is available as required... (a filter — unsatisfiable means Pending) or preferred... (a score — best effort).

Preemption

Pods can carry a PriorityClass. If a high-priority pod cannot be scheduled anywhere, the scheduler may evict lower-priority pods to make room. Useful, and worth knowing about before you discover it happening.

Scheduling happens once — the scheduler places a pod and then forgets it. It does not continuously rebalance. If the cluster becomes lopsided — because nodes were added, or because a burst of pods landed together — nothing moves existing pods to fix it. Rebalancing requires deleting pods so they get scheduled afresh, or a separate tool built for it.
07

Requests, limits, and the CPU/memory asymmetry

Two numbers per resource per container, and they do entirely different jobs:

  • request — what the scheduler reserves. Used for placement decisions. Not enforced at runtime.
  • limit — what the kernel enforces. Ignored by the scheduler.
The consequence — a container with a large limit and no request will be scheduled onto a node that cannot actually support it, because the scheduler was never told it needed anything. Requests are how you communicate with the scheduler; limits are how you communicate with the kernel. Setting only one of them means half the system is guessing.

CPU and memory behave completely differently

CPUMemory
NatureCompressible — can be given lessIncompressible — can't un-allocate
Exceeding the limitThrottled by CFS quota. Runs slower.OOMKilled immediately.
SymptomLatency, timeouts, no error anywhereExit code 137, container restart
DiagnosisHard — looks like a slow appEasy — it's in the pod status
CPU throttling is the nastiest resource bug in Kubernetes — nothing crashes, nothing logs an error, no event is emitted. The application is simply paused for part of every 100 ms period, and reports as tail latency that looks like a network or database problem. If a service is mysteriously slow under load, check container_cpu_cfs_throttled_seconds_total before anything else.

QoS classes — derived, not declared

Kubernetes assigns each pod a class based on what you set. It decides who gets killed first when a node runs out of memory.

ClassConditionEviction order
GuaranteedEvery container sets both, and request == limit, for CPU and memoryLast
BurstableAt least one request set, but not matching the aboveMiddle
BestEffortNo requests or limits at allFirst

You cannot set the class directly — it falls out of your numbers. Anything that must not be killed under pressure needs request equal to limit on both resources.

Node pressure and eviction

The kubelet watches memory, disk and inode pressure. Past a threshold it evicts pods — BestEffort first, then Burstable exceeding their requests, Guaranteed last. This is separate from OOMKill: eviction is a graceful Kubernetes-level decision that reschedules the pod elsewhere, whereas OOMKill is the kernel abruptly killing a process that crossed its own limit.

08

The network model: flat, and deliberately so

Kubernetes doesn't implement networking. It specifies a model and requires the CNI plugin to satisfy it. Three rules:

  1. Every pod gets its own IP address.
  2. Any pod can reach any other pod, on any node, without NAT.
  3. The address a pod sees for itself is the same address others use to reach it.
Why rule 3 sounds trivial and isn't — under Docker's default bridge networking, a container sees a private address while the outside world reaches it through a mapped host port. Anything that advertises its own address — service discovery, clustered databases, Kafka brokers publishing their listener address — breaks, because what it reports about itself is not usable by anyone else. Kubernetes forbids that entire class of bug by construction.

The cost is that pod IPs must be globally unique across the cluster, which is why you allocate a large private range up front and why it must not collide with anything else routable.

What a CNI plugin actually is

Far simpler than it sounds: an executable in /opt/cni/bin, configured by JSON in /etc/cni/net.d. The kubelet runs it with ADD when a pod starts and DEL when it stops, passing the network namespace path on stdin. ADD is expected to create the interface, assign an IP, set up routes, and print the result as JSON.

Everything a CNI implementation does beyond that — cross-node routing, encapsulation, NetworkPolicy enforcement — is its own design, not Kubernetes'. That is why plugins differ so much:

PluginApproachNetworkPolicy
FlannelVXLAN overlay, minimalNone
CalicoNative routing (BGP) or VXLAN; iptables/eBPF dataplaneFull, plus its own extensions
CiliumeBPF; can replace kube-proxy entirelyFull, including L7

Overlay vs native routing

Pod IPs aren't known to your physical network, so cross-node pod traffic has to get there somehow. Either encapsulate — wrap the pod packet inside a node-to-node packet (VXLAN, IPIP), which always works but adds header overhead and lowers effective MTU — or use native routing, telling the real network where each node's pod range lives (usually via BGP), which is faster but needs cooperation from your routers.

Middle ground: encapsulate only when crossing a subnet boundary. Nodes on the same L2 segment talk directly with no overhead; nodes further apart fall back to encapsulation automatically.

09

Services: a virtual IP that isn't on any interface

Pods are mortal and their IPs change constantly. A Service is a stable name and address in front of a set of them.

The ClusterIP is fiction

This is the part that confuses everyone, and it's worth stating plainly: a ClusterIP is not assigned to any network interface anywhere in the cluster. Nothing listens on it. You cannot ping it meaningfully. It exists only as a matching rule in the kernel's NAT tables on every node.

A pod sends to the Service
dst 10.96.14.7:80the ClusterIP
↓   netfilter, nat table   ↓
kube-proxy's rules — written from EndpointSlices
KUBE-SERVICESmatch on dst IP + port
DNAT, probabilisticpick one endpoint
↓   conntrack pins the flow   ↓
Delivered to a real pod
dst 192.168.115.12:8080rewritten; the pod never sees the ClusterIP

The rewrite is done by the kernel on the sending node, before the packet leaves. Load balancing is a probability chain across the endpoint rules; conntrack then pins that flow so every packet in the connection goes to the same pod.

Two consequences that bite — load balancing is per-connection, not per-request. A client holding one persistent HTTP/2 or gRPC connection sends every request to the same pod — which is why gRPC appears not to load balance at all. And because it's L4, the Service cannot inspect anything: no path routing, no header routing, no retries.

EndpointSlices

The Service's selector is evaluated continuously by the EndpointSlice controller, which maintains the list of Ready pod IPs backing it. kube-proxy watches these and rewrites its rules on change. Slices replaced the older single Endpoints object because one object listing every endpoint meant any single pod change pushed the entire list to every node.

Note Ready: a pod failing its readiness probe is removed from the slice, so traffic stops. This is the whole mechanism connecting readiness probes to load balancing.

Service types

TypeWhat it adds
ClusterIPDefault. Reachable only inside the cluster.
NodePortAlso opens the same port (30000–32767) on every node, forwarding to the Service.
LoadBalancerNodePort, plus asks an external controller for a real IP. On a cloud that's the provider's API; on bare metal it needs something like MetalLB, or the Service sits at <pending> forever.
ExternalNameNo proxying at all — just a CNAME in cluster DNS to an outside host.
Headless (clusterIP: None)No virtual IP and no proxying. DNS returns the pod IPs directly.
Headless is what makes StatefulSets work — a clustered system needs to address individual members, not a random one. Load balancing across Kafka brokers would be actively wrong — the client must reach the specific broker leading a partition. A headless Service gives each pod its own DNS record and gets the proxy out of the way entirely.
10

DNS: the naming scheme

CoreDNS runs as a normal Deployment in the cluster and is itself reachable through a Service. The kubelet writes that Service's address into every pod's /etc/resolv.conf. 

<service>.<namespace>.svc.cluster.local     # → the ClusterIP
<pod>.<service>.<ns>.svc.cluster.local   # → a pod, headless only

resolv.conf also carries a search list, which is why short names work: from inside namespace streaming, curl http://web resolves because web.streaming.svc.cluster.local is tried automatically. Cross-namespace needs web.other-namespace.

For a headless Service, a query for the Service name returns all pod IPs rather than one virtual IP — which is how a client discovers every member of a cluster in one lookup.

The search-path performance trap — ndots:5 is the default. Any name with fewer than five dots is tried against every search domain first. So api.github.com — two dots — generates several failing internal lookups before the real one succeeds. On a DNS-heavy service this is a measurable latency source, and the fix is a fully-qualified name with a trailing dot.
11

Getting traffic in from outside

Services solve pod-to-pod. External traffic is a separate problem with two answers, depending on whether the protocol is HTTP.

Ingress — HTTP only, L7

An Ingress object is pure configuration: a set of host/path rules and TLS settings. It does nothing by itself. An Ingress controller — nginx, Traefik, HAProxy — runs as a normal Deployment, watches Ingress objects, and reconfigures itself to match.

Because it terminates HTTP, it can do what a Service cannot: route by hostname and path, terminate TLS centrally, rewrite paths, load balance per-request rather than per-connection. One IP can serve many services.

The controller itself still needs to be reachable from outside — usually through a LoadBalancer Service. So Ingress sits on top of the Service mechanism, it doesn't replace it.

L4 — everything that isn't HTTP

RTMP, raw TCP, databases, anything binary: an Ingress controller cannot route it, because there are no hosts or paths to route on. These need a LoadBalancer Service directly — its own IP, its own port, no L7 layer involved.

The general rule — if the protocol carries a hostname the proxy can read, it can share an Ingress with everything else. If it doesn't, it needs its own address. That's the real reason a media server's ingest port and a web app get exposed by two different mechanisms.

Gateway API

Ingress's successor. It splits one overloaded object into several with distinct owners — GatewayClass and Gateway for the infrastructure team, HTTPRoute/TCPRoute for application teams — and standardises features that were previously vendor-specific annotations. It also handles non-HTTP protocols, which Ingress never did. Ingress is not going away, but new designs should look at Gateway API first.

12

NetworkPolicy: opt-in isolation

By default the flat network means every pod can reach every other pod in the cluster, across all namespaces. A compromised frontend can talk straight to your database. NetworkPolicy is how that gets restricted.

The rule that makes it make sense — a pod is unrestricted until it is selected by at least one NetworkPolicy. The moment one policy selects it for a direction (ingress or egress), that direction flips to default-deny and only explicitly allowed traffic passes. Policies are purely additive — there is no deny rule — so multiple policies union together.

The common idiom follows directly: apply a policy selecting everything with an empty allow list, which makes the namespace default-deny, then add narrow policies granting each real path. 

spec:
  podSelector: {}            # every pod in this namespace
  policyTypes: [Ingress]     # ...is now default-deny for ingress
  # no ingress: rules == allow nothing
Two things that catch people — policies are enforced by the CNI plugin, not by Kubernetes. Apply one under a plugin that doesn't implement NetworkPolicy — Flannel, for instance — and it is accepted, stored, and silently enforces nothing. Second: an egress policy that forgets to allow UDP port 53 to CoreDNS breaks all name resolution, which presents as "everything is broken" rather than as a policy problem.
13

Storage: decoupling the claim from the disk

Container filesystems die with the container. A Volume is declared in the pod and survives container restarts — but not the pod itself. Anything that must outlive the pod needs the PV/PVC pair.

ObjectRoleOwned by
PersistentVolumeA real piece of storage that existsCluster admin / provisioner
PersistentVolumeClaimA request: "10Gi, ReadWriteOnce"Application author
StorageClassA named recipe for creating PVs on demandCluster admin
Why the indirection — the application says what it needs; the cluster decides how to satisfy it. The same manifest that gets a local directory on a laptop cluster gets an EBS volume in AWS, with no change — because the PVC names a class of storage, not a device.

Dynamic provisioning

Without a StorageClass you must pre-create PVs by hand and hope one matches. With one, creating a PVC triggers the provisioner to create real storage and a matching PV automatically, then bind them.

The silent failure — if no default StorageClass exists, a PVC is accepted without error and sits in Pending — forever. The pod using it also sits in Pending, because a pod cannot start until its volumes are bound. Nothing reports an error; there is simply no provisioner listening. Every stateful workload will hang this way until a StorageClass exists, which is why it has to be the first thing installed before any database, broker or object store.

Access modes

  • ReadWriteOnce — one node may mount it read-write. Most block storage. Note node, not pod.
  • ReadOnlyMany — many nodes, read-only.
  • ReadWriteMany — many nodes, read-write. Needs a network filesystem; most block storage cannot do this.

ReadWriteOnce is why a Deployment with a PVC and more than one replica often deadlocks on rolling update: the new pod can't mount the volume until the old one releases it, and the old one won't terminate until the new one is Ready.

Reclaim policy

On PVC deletion: Delete destroys the underlying storage; Retain keeps it, requiring manual cleanup. Dynamic provisioning usually defaults to Delete — appropriate for scratch space, alarming for a production database.

CSI

The Container Storage Interface: the same idea as CRI and CNI. Storage vendors implement a standard gRPC API and ship a driver, instead of having code merged into Kubernetes itself. Every in-tree cloud storage plugin has been migrated out to CSI.

14

ConfigMaps and Secrets

Both hold key/value data and detach configuration from images. They are near-identical in mechanics and differ mainly in handling.

Secrets are not encrypted — the values are base64-encoded, which is an encoding, not encryption, and trivially reversible. By default they are stored in etcd in plaintext. Encryption at rest is a separate opt-in feature the cluster operator must configure. Anyone who can read a Secret through the API, or read etcd, has the value.

What Secrets do give you: separate RBAC (you can grant ConfigMap access without Secret access), exclusion from most logging and describe output, and tmpfs mounting so values never touch node disk. Real protection needs encryption at rest, tight RBAC, and keeping the source of truth outside git — encrypted-in-repo tooling, or an external secret store.

Environment variable vs volume mount

As env varAs mounted file
Update on changeNever — fixed at container startYes, automatically (up to ~a minute)
Visible in/proc/<pid>/environ, child processes, crash dumpsOnly the file
Best forSmall, static valuesCertificates, anything rotated
The trap in that first row — updating a ConfigMap consumed as environment variables changes nothing in running pods, and no error is raised anywhere. The pods must be restarted. Mounted files update in place, but the application still has to notice and re-read them — the file changing does not reload your config by itself.
15

Authentication, ServiceAccounts, RBAC

Two kinds of identity

  • Users — humans. Kubernetes has no user object and no user database. Identity comes from an external source: a client certificate's subject, an OIDC token, an authenticating proxy. A "user" is whatever the authenticator says it is.
  • ServiceAccounts — real API objects, for processes inside the cluster. Every pod gets one (default if unspecified) and a token mounted at a well-known path.

RBAC

Four object types, in two pairs:

ObjectSaysScope
RoleThese verbs on these resourcesOne namespace
ClusterRoleSame, including cluster-scoped resourcesWhole cluster
RoleBindingGrants a Role (or ClusterRole) to subjects in one namespaceOne namespace
ClusterRoleBindingGrants a ClusterRole everywhereWhole cluster
The property that makes RBAC predictable — it is purely additive. There are no deny rules. Permission is the union of every binding that applies to you, and nothing can subtract from it. So "why can this account do X?" always has a findable answer — some binding grants it — but revoking access means finding and removing every grant, not adding a denial.

A useful combination that's easy to miss: binding a ClusterRole with a RoleBinding grants those permissions only within that namespace. That's how you define a role like "read pods and logs" once and reuse it per-namespace.

The pod-level escalation path — RBAC guards the API, but a pod granted host access can bypass it entirely. privileged: true, hostPID, hostNetwork, or a hostPath mount of / all lead to node root, and node root reads every Secret of every pod on that node. Pod Security Admission exists to enforce limits on those fields, and a cluster with careful RBAC but no pod security policy has a fairly short path around it.
16

Admission control

Between authorization and persistence, every request passes through admission controllers — the last chance to modify or reject an object, and the mechanism behind most cluster-wide policy.

  • Mutating admission runs first and can change the object: injecting sidecars, adding default labels, setting resource defaults from a LimitRange.
  • Validating admission runs second and can only accept or reject: enforcing required labels, blocking :latest tags, rejecting privileged pods.

Both can be extended with webhooks — the API server calls your HTTPS endpoint with the object and uses your verdict. This is how service meshes inject proxies automatically and how policy engines enforce organisational rules.

Webhooks are in the critical path — a webhook configured failurePolicy: Fail whose backing pods are down blocks every matching API write in the cluster. If the webhook's own namespace is in scope, you get a deadlock: the pods can't start because admission is failing, and admission is failing because the pods can't start. Namespace exclusions on system namespaces exist precisely for this.

Newer clusters also support ValidatingAdmissionPolicy — CEL expressions evaluated inside the API server, no webhook server to run or keep alive. Less powerful than a webhook, but with none of the availability risk.

17

CRDs and operators: extending the model

A CustomResourceDefinition registers a new object kind with the API server. After applying one, the cluster has a genuinely new resource type — with the same schema validation, kubectl support, RBAC, watch semantics and spec/status shape as any built-in.

A CRD alone does nothing at all. It gives you a place to store structured data. On its own, applying a custom resource achieves exactly as much as writing to a database.

Operator = CRD + controller — the pattern is: define a resource describing what you want, then run a controller that watches it and reconciles the world to match — the exact loop from §1. A Kafka resource describing a three-broker cluster is inert until a controller reads it and creates the StatefulSets, Services, ConfigMaps and PVCs that constitute one. The operator encodes what a human operator would otherwise do by hand, including the hard parts — ordered upgrades, failover, rebalancing.

This is why so much infrastructure ships as an operator now. The pattern is uniform enough that you can predict the shape of an unfamiliar one: install CRDs, install the controller, apply a custom resource, watch its status converge.

Install order is not optional — CRDs must be registered before any resource of that kind is applied, or the API server rejects it with no matches for kind — it genuinely does not know the type exists yet. Some projects bundle CRDs with the controller manifest and some ship them separately, so this is a frequent first-run failure. Deleting a CRD is worse: it deletes every object of that kind in the cluster.
18

Full trace: kubectl apply to serving traffic

Everything above, in sequence. Watch how no component ever calls another — each only reads and writes objects, and the next one notices.

kubectl Reads your YAML, resolves the resource type, and issues an HTTP request to the API server. Nothing clever happens client-side.
kube-apiserver Authenticates you, checks RBAC, runs mutating admission (defaults get filled in), validates the schema, runs validating admission, and writes the Deployment to etcd. The request returns here — the object exists, and not one container has been created.
deployment controller Its watch fires. It sees a Deployment with no matching ReplicaSet for this pod template, so it creates one with replicas: 3, stamped with an ownerReference back to the Deployment.
replicaset controller Its watch fires. Desired 3, observed 0. It creates three Pod objects — each with spec.nodeName empty, because placement is not its job.
kube-scheduler Sees three unbound pods. For each: filters nodes that can't fit or don't tolerate, scores the rest, picks one, and writes a Binding — setting nodeName. Still nothing running.
kubelet On that node, notices a pod now bound to it. Calls the CRI to pull images and create the sandbox — the pause container holding the namespaces — then calls the CNI plugin, which creates the interface and assigns a pod IP.
kubelet Mounts volumes, projects ConfigMaps and Secrets, runs init containers to completion, then starts the app containers. Begins running probes.
kubelet Writes observed state into the pod's status — phase, IP, container states. When the readiness probe passes, the Ready condition flips to true.
endpointslice controller Sees a newly-Ready pod whose labels match a Service selector, and adds its IP to that Service's EndpointSlice.
kube-proxy On every node, sees the EndpointSlice change and rewrites the local NAT rules so the Service's ClusterIP can now DNAT to this new pod. Traffic starts flowing to it.
deployment controller Watches replica counts climb, updates the Deployment's status, and — during a rollout — scales the old ReplicaSet down as the new one becomes available, within maxSurge/maxUnavailable.
The thing to take from this — eleven steps, zero direct calls between components. Every handoff is "write an object" followed by "someone else's watch fires". Add a new controller and it participates in exactly the same way. Remove one and the pipeline simply stalls at that point, with the objects sitting there describing precisely how far it got — which is why kubectl get at each level tells you where something is stuck.

Reading failures

Most Kubernetes debugging is locating which loop is stuck. The trace above is the map: find the last step that completed, and the problem is in the next one.

SymptomStuck atUsual cause
Pending, no node assigned Scheduler filtering Insufficient resources, unsatisfiable affinity, untolerated taint. The events say which.
Pending, node assigned Kubelet, before start Volume won't mount — often a PVC with no provisioner.
ContainerCreating, stuck CNI or volume mount CNI plugin failing to allocate, or a missing ConfigMap/Secret referenced by the pod.
ImagePullBackOff CRI image pull Wrong name/tag, private registry with no imagePullSecret, or rate limiting.
CrashLoopBackOff The container itself It starts and exits. Kubernetes is working correctly — logs --previous has the answer.
Exit code 137 Kernel OOM killer Exceeded its memory limit. Raise the limit or fix the leak.
Running but no traffic EndpointSlice Readiness probe failing, or the Service selector doesn't match the pod labels. Check for zero endpoints.
Intermittent slowness under load CFS throttling CPU limit too low. Silent — no event, no log, no restart.
Service <pending> forever No LB controller type: LoadBalancer on bare metal with nothing implementing it.
Namespace Terminating forever A finalizer A controller that owed cleanup is gone. Usually a removed operator.
The three commands that answer most of it — kubectl describe for events and conditions (the events at the bottom are usually the whole answer), kubectl logs --previous for a container that already died, and kubectl get endpointslices when something is running but unreachable.

Glossary

Reconciliation loop
Continuously compare desired state to actual state and take one step to close the gap. The core pattern of the entire system.
Level-triggered
Acting on current state rather than on events. Makes controllers tolerant of crashes, missed messages and duplicates.
Controller
Any process running a reconciliation loop over some resource.
Operator
A controller for a custom resource — domain knowledge about running a specific system, encoded as software.
spec / status
Desired state, written by you / observed state, written by a controller. Debug the second.
Pod
The scheduling unit: containers sharing a network namespace, IPC and volumes. Has the IP.
Sandbox / pause container
The near-empty container that holds a pod's namespaces open so containers can restart without losing the IP.
ClusterIP
A virtual address that exists only as kernel NAT rules. Not assigned to any interface.
EndpointSlice
The live list of Ready pod IPs behind a Service. What kube-proxy programs from.
Headless Service
clusterIP: None — DNS returns pod IPs directly, no proxying. How StatefulSet members are addressed.
CRI / CNI / CSI
The runtime, network and storage plugin interfaces. Kubernetes defines the contract; vendors implement it.
Taint / toleration
A node repelling pods / a pod's exemption from a specific taint.
QoS class
Guaranteed, Burstable or BestEffort — derived from your requests and limits, and it sets eviction order.
Requests / limits
What the scheduler reserves / what the kernel enforces. CPU over limit throttles; memory over limit kills.
PV / PVC / StorageClass
Storage that exists / a request for storage / a recipe for creating it on demand.
Finalizer
A string blocking deletion until its controller does cleanup and removes it. Cause of most stuck deletions.
ownerReference
A child's pointer to its parent. Drives cascading deletion.
Admission controller
Runs between authorization and storage; mutating ones rewrite objects, validating ones accept or reject.
CRD
Registers a new resource kind with the API server. Inert without a controller watching it.
The short version

Kubernetes stores the world you want and runs dozens of small loops that each fix one kind of difference between that and the world you have. It is level-triggered, so it converges from any state rather than depending on a correct sequence of events. Everything moves through one API, which is why one auth model, one audit log and one extension mechanism cover the whole system.

Components never call each other. They write objects and watch objects. Understanding any feature — built-in or third-party — reduces to two questions: which object holds the desired state, and which controller is watching it?

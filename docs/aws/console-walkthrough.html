Chapter 1General Information

1-1. Scope

1-1.1 This manual contains the installation procedures for the streaming platform on Amazon Web Services, expressed as management console navigation. Each procedure states the screen to be opened, the decision that screen represents, the fields requiring deliberate selection, the verification criterion, and the failure modes associated with that step.

1-1.2 Commands and configuration file listings are not reproduced here. Where a step cannot be performed from the console, that fact is stated and the module containing the command is cited.

1-2. Applicability

1-2.1 This manual assumes the operator has been issued an IAM role and has no prior familiarity with the management console. No other qualification is assumed.

1-2.2 System description, architecture and installation planning are contained in TM SP-1, which shall be read first.

1-3. Arrangement of procedures

1-3.1 Procedures shall be performed in the order presented. Each is arranged as follows:

  • Navigation. The console path, given as a breadcrumb.
  • Function. The decision the screen represents. This is the instructional content and shall be read before the fields are set.
  • Fields. Only those requiring deliberate selection. Fields not listed may be left at their default values.
  • Verification. The condition confirming the step is complete.
  • Failure modes. The faults associated with the step, in order of observed frequency.
NOTE

The console is used here as the instructional surface. The deployment course builds the cluster from a configuration file, which is the correct method for infrastructure that is to be retained. A configuration file is not readable until its field names are known, and the console is where they are learned. Every field in that file exists as a labelled control on a screen in this manual.

1-4. Division of effort between console and command line

1-4.1 The division is not entirely a matter of preference. The management console creates AWS resources. It cannot create Kubernetes objects, which are held by a separate API server operating within the cluster.

Table 1-1. Division of effort between console and command line.
MediumApplies toRemarks
ConsoleBudget, cost reporting, IAM inspection, database, object storage, content delivery, name service, certificatesCreated once and seldom modified. The console is faster for these and teaches the field names.
Configuration file (eksctl)VPC, cluster, node group, identity provider, access entries, cluster add-onsOne interlocking unit. Disposal is a single operation rather than an exercise in recollection.
Command line (kubectl, helm)All Kubernetes objects; all platform controllersNo console equivalent exists. Chapters 4 (paragraph 4-6) and 5 in their entirety.

1-4.2 The cluster console provides a resources view which will display Kubernetes objects. It is adequate as a read-only inspection aid and shall not be relied upon for creation.

1-4.3 Diagnostic application. When a fault is observed, determine first which side of table 1-1 it lies on. A pod in a pending state is a Kubernetes-side condition and no amount of console inspection will reveal the cause; the cause is recorded in that object's events.

1-5. Advisory conventions

1-5.1 Advisories are used as defined in TM SP-1, paragraph 1-4. WARNING denotes unrecoverable loss, unbounded expenditure or loss of access. CAUTION denotes a failed step or wasted expenditure. NOTE denotes clarifying information.

Chapter 2Preparation for Use

2-1. Access credentials

2-1.1 A role is not an account. A user is a permanent identity holding a password and possibly long-lived keys. A role is a set of permissions belonging to no one; it is assumed temporarily, and the credentials issued expire within hours.

2-1.2 Three consequences follow, all of which are normal behaviour and not faults:

  • Sessions expire. This is the purpose of the design. A credential that expires cannot be used a year after it is taken.
  • The identity has a readable form. The console displays the role name and account number at upper right. That string is the principal, and it is the principal that is named when access is denied.
  • No action is anonymous. Every call is recorded against the principal in the audit trail. This is how the cause of a deletion is later established.

2-2. Verification of granted permissions

NavigateIAM›Roles›[your role name]›Permissions

2-2.1 Inspect the policies attached to the issued role before any work is attempted. The result determines whether the remainder of this manual can be executed without assistance.

Table 2-1. Permission profiles and their consequence.
Observed policyConsequence
AdministratorAccessAll procedures in this manual may be executed. Exercise care rather than relief.
PowerUserAccessAll procedures except the creation of IAM roles, which the cluster requires repeatedly. Obstruction will occur at paragraph 3-2. Identify the party who can create roles before proceeding.
A written policyInspect for authority over iam:CreateRole, iam:PassRole, eks, ec2 and rds actions. Absence of PassRole is the least obvious and most obstructive.
CAUTION

Several components created in this manual do not act as the operator; they act as a role handed to them. The control plane assumes a role, nodes assume a role, the database assumes a role for logging. Handing a role to a service is itself a privileged act, gated separately as iam:PassRole, because otherwise any party able to launch an instance could launch it with administrative authority.

The resulting symptom is a successful creation form followed by an access denial naming PassRole. This is not a fault in the form.

2-2.2 Two halves of the permission model. Identity policies attach to the operator and state what may be done. Resource policies attach to an object and state who may act upon it. Most services require only the identity side; object storage and key management require both sides to agree. This is why an object storage denial is sometimes not corrected by granting the operator additional permissions.

Verification

The operator can state the name of the issued role, whether it may create IAM roles, and who is to be asked if it may not.

2-3. Console orientation

2-3.1 Region selector. Located at upper right. Nearly every resource exists in exactly one region and is not visible from any other. The characteristic first-week fault is creating a cluster, returning the following day to an empty list, and concluding it was deleted, when the console has reset to a different region. This project uses us-east-1.

NOTE

Certain services are global and will display as us-east-1 or as Global: identity management, name service, content delivery and billing. These have no region. A consequence is that a certificate intended for the content delivery network shall be requested in us-east-1 specifically. See paragraph 4-2.

2-3.2 Search field. The search field at the top of every page is the primary navigation. It resolves both service names and individual resource identifiers. Every navigation path in this manual begins with a service name that may be entered there.

2-3.3 Resource names. Every object carries an Amazon Resource Name stating partition, service, region, account, type and identifier. Resource names are entered into policies and are quoted in error messages. Familiarity sufficient to read one at a glance is required.

2-3.4 Tagging. Nearly every creation form carries a tags section near the bottom, and it is nearly always skipped. A consistent project tag shall be applied to every resource created. Two benefits accrue later: the bill may be filtered by that tag, and disposal may enumerate by that tag rather than by recollection.

2-3.5 Status of the console. The console is a client calling the same interface as the command line. No capability is console-only. When a form fails, the message displayed is generally the unmodified interface error and is generally precise.

2-4. Cost control provisions

NavigateBilling and Cost Management›Budgets›Create budget
WARNING

A budget is not a limit. Expenditure will not be halted when the figure is reached. A budget observes spending and issues notification; no resource is stopped and no service is suspended. No facility exists to cap an account at a chosen figure.

This provision shall be completed before any chargeable resource is created.

Table 2-2. Budget configuration fields.
FieldSelection criteria

Billing data is restricted separately from all other permissions. By default only the account management identity may view it, and account administrators may be refused until access to billing data is enabled in the account settings. If the budgets page is inaccessible, this is the cause. It is a brief correction for the account owner and shall be requested before construction begins.

2-4.1 Cost reporting. Enable cost reporting at Billing and Cost Management›Cost Explorer at this time. Collection begins when enabled and cannot be applied retroactively to preceding days. When expenditure later requires explanation, group by service to identify the category, then by usage type to identify the line item. The second grouping is where it is discovered that a substantial share of cost is network address translation data processing rather than the compute that was assumed.

Verification

Budget creation is confirmed and cost reporting is enabled. Chargeable resources may now be created.

2-5. Workstation preparationLocal machine

2-5.1 Four tools are required. The reason each is required is stated, as the requirement is not arbitrary.

Table 2-3. Required workstation tools.
ToolFunction within this deployment
AWS CLICommunicates with AWS. Principally required for the one operation the console cannot perform: writing the file that permits kubectl to authenticate to the cluster.
kubectlCommunicates with Kubernetes. Deployments, services, ingresses, secrets and jobs are held by the cluster's own interface and are not AWS resources.
HelmInstalls the platform controllers: ingress, autoscaling, secrets synchronisation, message broker. These are distributed as charts and have no console equivalent.
eksctlConstructs the cluster from a single configuration file. Its failure messages are readable, which is the principal argument for it at this scale.

2-5.2 Credential resolution. When any AWS tool requires credentials it examines a fixed sequence of locations — environment variables, then a named profile in the configuration file, then any role attached to the machine — and uses the first found. Nearly every instance of a command acting on the wrong account is caused by an entry earlier in that sequence than was assumed.

2-5.3 Where the role is issued through a sign-on portal, a profile is configured naming the portal and the role, and signing in caches short-lived credentials. Where the role is assumed from a base user, the profile names the role and its source. In either case a named profile shall be used and the default profile shall not. The default profile is the mechanism by which deletions are executed against the wrong account.

Verification

A single command reports the identity AWS currently attributes to the operator. It shall be executed at the start of every session, and before any resource is touched. If the role reported is not the role expected, work shall stop until it is. The command is given in Module 1.

CAUTION

Tool versions are significant. kubectl is supported only within one minor version of the cluster, and eksctl shall be recent enough to recognise the cluster features in use. An unrecognised-field error is far more often an obsolete tool than an incorrect configuration. Versions are pinned in Module 1.

Chapter 3Platform Installation

3-1. Network

CAUTION

This procedure is performed for instruction only. The screens shall be completed and then cancelled. infra/eks/cluster.yaml constructs the network as part of the cluster; a network constructed here by hand would be a second, unused one, carrying a network address translation gateway billing approximately $33 per month to carry no traffic.

Complete the wizard. Study what it draws. Cancel.

NavigateVPC›Your VPCs›Create VPC›VPC and more

3-1.1 Purpose of the procedure. Select "VPC and more" rather than "VPC only". The latter produces an empty network to be furnished by hand. The former constructs the complete set from a small number of answers and, materially, renders the resulting network as a diagram at the right of the screen which updates as options are changed.

3-1.2 That preview is the instructional value of the screen. Alter the zone count and observe subnets multiply. Change address translation from one gateway to one per zone and observe gateways appear. Enable the object storage endpoint and observe where it attaches. This costs nothing because the form is to be cancelled.

3-1.3 The decision represented by this screen reduces to one question: which components shall be reachable from the internet, and by what means shall the remainder reach outward.

Table 3-1. Network wizard fields.
FieldMeaning and selection criteria
IPv4 CIDRThe private address range for the network. The significant property is size: in EKS every pod draws a real address from the subnets, so pod count is bounded by address space. A /16 is generous and carries no charge. A small range shall not be selected for tidiness.
Availability zonesPhysically separated facilities. One is fragile and prevents certain managed services from operating, as the database requires two subnets in separate zones. Two is the frugal selection. Three is the default applied by eksctl when the configuration is silent, and is what this project receives.
Public subnetsCarry a route to the internet gateway. Load balancers reside here. No other component requires it.
Private subnetsCarry no inbound route from the internet. Nodes and the database reside here. This is the default location for any component not deliberately published.
NAT gatewaysThe expenditure decision on this screen. See paragraph 3-1.4.
VPC endpointsEnable the object storage gateway endpoint. It carries no charge and keeps object storage traffic off the address translation gateway. This single control can represent a material share of the bill.
DNS hostnames and resolutionBoth enabled. EKS requires them and failures in their absence are obscure.

3-1.4 Address translation. Components in private subnets still require outbound access to retrieve container images and call service interfaces. A network address translation gateway permits outbound without inbound. It is charged per hour and per gigabyte processed, and is generally the second-largest item on a cluster bill after the control plane.

3-1.5 The wizard offers one gateway per zone, which is resilient, or one in total, which is cheaper but surrenders outbound access for all private subnets if that zone becomes unavailable. This project specifies one, and cluster.yaml records the monthly difference in a comment beside the setting. The requirement is that the operator can state which was selected and what is forfeited by it.

3-1.6 Subnet tagging. When an ingress is later created, a controller within the cluster shall determine which subnets are to receive a load balancer. It does so by reading specific tags on the subnets, one marking a subnet as suitable for internet-facing balancers and another for internal ones. Recent configurations can often determine this automatically; where a load balancer fails to appear and the controller log refers to subnet discovery, this is the cause.

3-1.7 Because eksctl creates these subnets it also tags them correctly, which is among the quieter arguments for permitting it to do so. The location is recorded for inspection, as an absent tag is undetectable until an ingress fails to produce anything:

InspectVPC›Subnets›[subnet]›Tags

3-1.8 Security groups. A security group is a stateful filter attached to a resource, not to a subnet. Two properties are significant and both are counter-intuitive:

  • Allow rules only. No deny rule exists. Traffic not permitted is refused by omission.
  • Stateful. Where an inbound connection is permitted, the reply is permitted outbound automatically. Return rules are not written.

3-1.9 The source of a security group rule may be another security group rather than an address range. "Permit database traffic from the cluster's security group" is both more legible and more correct than any address range, as it remains valid as node addresses change. This construction is used at paragraph 4-3.

3-1.10 Correlation with the configuration file. Close the console and open the vpc: block of infra/eks/cluster.yaml. Every field just completed appears there under a different name, as shown in table 3-2.

Table 3-2. Wizard field to configuration file mapping.
Wizard fieldFile fieldRemarks
IPv4 CIDRvpc.cidrA /16, per paragraph 3-1.3.
NAT gatewaysvpc.nat.gatewaySet to a single gateway, with the cost of the selection recorded in an adjacent comment.
Availability zonesAbsentNot stated, so the tool default applies. An unwritten field remains a decision; this one procures three zones.
Public and private subnetsDerivedThe subnet layout is computed from the address range and zone count. The shape is described and the arithmetic is performed by the tool.

NOTE

Read without preparation, gateway: Single conveys nothing. Read ten minutes after observing the wizard diagram gain and lose a gateway as that same control was changed, it conveys a specific quantity, and the operator is able to weigh $66 per month against the consequence of a zone failure because the consequence has been seen in both configurations.

This is the method of the manual as a whole: concepts carry labels and diagrams in the console; decisions are recorded in the configuration file. Learn in the first, construct with the second.

Verification

The operator can identify each field in the vpc: block of cluster.yaml and state what it will create, and no network has been created in the console.

3-1.11 Failure modes. A network created here notwithstanding the CAUTION, then forgotten; inspect VPC›Your VPCs for strays before proceeding. Address space specified too small, discovered months later when pods cannot obtain addresses. DNS hostnames left disabled. Object storage endpoint omitted, discovered on the bill.

3-2. Cluster

CAUTION

As paragraph 3-1. cluster.yaml creates the cluster, node group and core add-ons together with the network; they are one interlocking unit and are constructed as one. Walk these screens for instruction, cancel, and construct from the file. Paragraphs 3-2, 3-4 and 3-5 each correspond to a stanza of that file, identified in the paragraph heading.

NavigateEKS›Clusters›Create cluster

3-2.1 What is procured. A Kubernetes control plane: interface server, scheduler, controller manager and the state store behind them, operated across multiple zones by the provider, patched by the provider, at a fixed hourly rate. The machines are never seen. What is delivered is an interface endpoint and an availability commitment.

3-2.2 No capacity to run workloads is procured by this step. That is paragraph 3-4 and is billed separately. A cluster with no nodes is permissible, performs no function, and costs approximately $73 per month, which is the reason chapter 6 exists.

3-2.3 Managed compute mode. The creation screen offers a mode in which compute, storage and load balancing are managed by the provider: nodes appear on demand, a storage class exists, ingress functions, with nothing installed by the operator. A percentage premium is charged above the instance rate.

NOTE

Where the objective is to operate the application with minimum operational surface, that mode is a sound selection. Where the objective is to learn the function of those controllers, its entire value consists of concealing them. The course installs them individually for that reason; the storage driver, load balancer controller and node autoscaler are met separately at paragraphs 3-5 and 5-4. Selecting the manual path is an exchange of effort for understanding and shall be made deliberately.

3-2.4 Screen 1 — cluster configuration. Fields per table 3-3.

Table 3-3. Cluster configuration fields.
FieldSelection criteria
NamePermanent. It appears in resource names, in the local configuration file, and in the names of every generated identity role.
Kubernetes versionNot the newest offered. Match the version the manifests were written against; this project pins the version used by the rehearsal cluster, so that behaviour learned there transfers unchanged. Confirm the duration of standard support for that version, as extended support is charged at a higher hourly rate.

3-2.5 Screen 2 — networking. The console requires an existing network and subnets to be selected, which is precisely the step the configuration file removes: because it creates network and cluster together, it is never required to ask. The distinction between the two methods is visible in this one screen. Selecting by hand requires the network to exist first; the file describes both and permits one tool to resolve the order.

3-2.6 Two fields warrant consideration under either method:

  • Subnets. The private subnets host the cluster's own network interfaces. Public subnets are for load balancers, which a controller creates later; they need not be the cluster's residence.
  • Cluster endpoint access. Public, private or both. This is vpc.clusterEndpoints from table 3-2. Public indicates the Kubernetes interface is reachable from the internet — authenticated, but reachable. Private restricts it to within the network, which is safer and requires a bastion or private connection for any administrative command. This project specifies both, together with a permitted-range field presently left open and annotated to be narrowed where a fixed address is available. This concerns the administrative interface only and not application traffic; the two are unrelated.

3-2.7 Screen 3 — add-ons. The networking plugin, name service and proxy component are offered, together with an optional storage driver and workload identity agent. Accept the defaults and add the identity agent. The remainder may be added at paragraph 3-5. Nothing at this screen is irreversible.

WARNING

The identity that creates the cluster is granted Kubernetes administrative rights automatically. Where a colleague creates the cluster with their role, or where the operator creates it while assuming a role other than the one used routinely, authentication will succeed and every subsequent action will be refused, without the reason being stated.

The cluster shall be created as the role that will be used to operate it. Paragraph 3-3 is the corrective action where it was not.

Verification

Cluster status advances from creating to active. Elapsed time is approximately ten to fifteen minutes; this does not indicate a stalled operation.

3-3. Cluster access

3-3.1 This is the least intuitive element of the platform and warrants unhurried attention. Once understood, an entire category of faults becomes self-explanatory.

Figure 3-1. Authentication and authorization sequence.

3-3.2 Two independent systems operate in sequence. AWS establishes identity; Kubernetes establishes authority. The connection between them is an access entry: a record stating that a given AWS principal corresponds to a given Kubernetes identity.

NavigateEKS›[cluster]›Access›Create access entry

3-3.3 The entry names an identity role and attaches an access policy: the cluster administrator policy for the operator, narrower policies for others. The screen is brief; the concept is the substance.

NOTE

An explicit entry shall be created for the operator notwithstanding the automatic grant described at paragraph 3-2. The automatic grant is bound to the exact principal that performed the creation. Where a sign-on role is recreated, which occurs when permission sets are amended, it returns with a different internal identifier and the automatic grant no longer corresponds. An explicit entry survives this. It appears redundant; it is what prevents loss of access to the operator's own cluster.

3-3.4 Workstation connection.Command line One command writes a local configuration entry for the cluster. What is written warrants understanding: not a password, but an instruction directing the administrative tool to request a token from the AWS command line on each connection. Consequently cluster access expires with the AWS session, and restoring access generally means re-authenticating to AWS rather than altering anything in Kubernetes. The command is given in Module 3.

Verification

A node listing returns a result, including the response indicating no resources were found, which is the correct result before paragraph 3-4. That response confirms passage through both permission systems.

3-3.5 Distinguishing the two failures. A message stating the operator must be logged in to the server, or reporting unauthorized status, originates on the AWS side: credentials are incorrect or expired. A message reporting forbidden status and naming a resource that cannot be listed originates on the Kubernetes side: entry succeeded but the access entry does not confer that authority. These are separate conditions with separate corrections, and distinguishing them conserves substantial time.

3-5. Cluster add-onsFile stanza: addons

NavigateEKS›[cluster]›Add-ons›Get more add-ons

3-5.1 A bare cluster cannot perform several functions that are commonly assumed present. Each add-on is a controller, and each is properly understood as a program that observes Kubernetes objects and causes AWS to act.

3-5.2 Two are required at this stage:

  • Block storage driver. Without it a pod requesting a volume waits indefinitely. The message broker requests a volume. Install it now, and afterwards confirm a storage class is marked default.
  • Workload identity agent. Prerequisite to paragraph 3-6.

A storage driver installed without a default storage class produces precisely the same symptom as no driver at all: volume requests remain pending with no informative message. Confirm the default marking as a separate act from the installation.

3-6. Workload identityFile stanza: iam.withOIDC

3-6.1 The upload service requires write access to object storage. The secrets controller requires read access to the secret store. Neither shall contain an access key, as a key within a container image is a key within version control, within the registry, and upon every machine that has retrieved it.

3-6.2 The mechanism substituted is shown in figure 3-2.

Figure 3-2. Workload credential issue sequence.
NavigateEKS›[cluster]›Access›Pod Identity associations›Create
NOTE

Two mechanisms exist and this project requires both. The earlier, identity roles for service accounts, operates through an identity provider: the cluster publishes a provider and each role's trust policy names the service account permitted to assume it. The later, pod identity, substitutes a plain association created through the service interface, requiring no provider and no trust policy amendment, and permitting roles to be reused across clusters.

Pod identity is simpler and is what the application services use. Several widely used controllers, including the load balancer controller and the node autoscaler, still require the earlier mechanism, so the provider shall exist as well. It shall be enabled at cluster creation rather than added afterwards. This is the practical consequence of an ecosystem mid-transition.

CAUTION

Credentials are resolved when a pod starts. An association created while the pod is already running will continue to produce access denials until the pod is restarted. The association is correct; the running pod precedes it. Restart before commencing diagnosis.

3-6.3 Two further practices apply. One role shall be created per service rather than one shared role; this is additional configuration, and it ensures that a compromised transcode job cannot read the database credential. Denials shall be read literally; an AWS denial names the action, the resource and the principal, all three of which are generally accurate. The action indicates the permission to be added; the resource indicates whether the correct object was addressed at all.

Chapter 4Data Services Installation

4-0.1 The data layer shall be installed before the application, per TM SP-1 paragraph 4-1.2.

4-1. Name delegation

NavigateRoute 53›Hosted zones›Create hosted zone

4-1.1 A domain is not being purchased; authority is being claimed over a subdomain of one already in existence. Creating the zone yields four name server records, which have no effect until the party operating the parent domain publishes a delegation directing the subdomain to them.

4-1.2 Delegation. The name service is a chain of referrals. A resolver seeking the hostname interrogates the parent zone, which replies that authority lies elsewhere and names four servers. That referral is the delegation. Until the parent publishes it, the zone is a valid set of records to which no resolver in the world will be directed. The symptom of an absent delegation is therefore not an error but silence.

CAUTION

Transmit the four records to the operator of the parent zone before this step is required by the schedule. Propagation requires minutes to hours; obtaining the action from another party is the element that consumes a day.

4-2. Certificate

NavigateCertificate Manager›Request certificate›Request a public certificate

4-2.1 Public certificates are issued without charge and renew automatically, but only where validation is performed by name service record rather than by electronic mail, as a record can be re-examined indefinitely and a message link cannot. Name service validation shall be selected.

4-2.2 Request one certificate covering the names to be served. A wildcard covers one level of subdomain and is generally the tidiest selection. Following the request the screen offers to create the validation records automatically; this shall be used. Status remains at pending validation for several minutes and then advances to issued.

CAUTION

A certificate is regional and a load balancer may use only one from its own region. The content delivery network, being global, accepts certificates only from us-east-1. Where work is performed in another region and the distribution does not offer the certificate, this is the cause, and the correction is a second certificate requested in us-east-1. This project operates in us-east-1 throughout and does not encounter it, but the condition shall be known.

Verification

The certificate reports issued status, and a public lookup of any name in the zone reaches the name service rather than nothing.

4-3. Database

WARNING

Block all public access shall remain enabled. Every instinct will suggest disabling it so that browsers may retrieve video; it shall not be disabled. The content delivery network is granted private access instead, which is both more secure and less costly, as public bucket reads are charged at storage rates rather than delivery rates.

4-4.1 Two settings warrant deliberate selection rather than acceptance:

  • Versioning. Useful, but every overwrite retains the prior copy and prior versions are charged as objects. Where enabled, it shall be paired with a lifecycle rule expiring them; otherwise this becomes a disposal obstruction, as a bucket holding versions cannot be deleted until they are removed.
  • Lifecycle rules. Video accumulates. The retention period for segments and recordings shall be decided now and recorded as a rule rather than retained as an intention.

Table 4-2. Distribution configuration fields.

4-5.2 Two cache behaviours are required. An HLS stream comprises two classes of file with opposing cache requirements. Segments are immutable: once written the file never changes, and shall be cached at length. The playlist is rewritten every few seconds to announce new segments, so caching it even briefly causes players to re-read a stale list and the stream to appear frozen.

4-5.3 Accordingly a second cache behaviour shall be added matching the playlist path with caching effectively disabled, leaving the default behaviour aggressive for all other paths.

CAUTION

Where the two behaviours are transposed, the symptom is a stream that begins and then ceases to advance. This presents as a transcoding fault and is not one.

Distribution amendments deploy across the global edge network and require several minutes. Where a cache setting is changed and no effect is observed, the change is probably correct and merely early. Invalidation of cached paths is available and is charged beyond a free allowance; it shall be used for the playlist during testing and not as routine practice.

4-6. Message brokerCommand line — entirely

4-6.1 No console procedure exists for this component, and the reason constitutes the instruction. The broker here is not a provider service; it is software operating within the cluster, installed by operator.

NOTE

Kubernetes is able to operate deployments and services. It has no knowledge of the broker. An operator supplies that knowledge: a controller is installed which registers new object types, such as broker cluster and broker topic, and operates a loop observing those objects and performing whatever work causes reality to correspond to them. Create a topic object and the operator creates the topic. Delete a broker pod and the operator observes the deficiency and rebuilds it.

This pattern recurs at the node autoscaler in paragraph 5-4, the secrets controller, and the deployment agent in paragraph 5-5. It is the most transferable concept in the platform.

4-6.2 The sequence is: install the operator by chart, then declare a broker cluster and the required topics as manifests to be applied. Persistent storage shall be operational, so the storage driver and default storage class from paragraph 3-5 are prerequisite. Where brokers remain pending, that is the cause in every observed instance. Manifests are given in Module 10.

4-6.3 Partitioning. Messages shall be partitioned by stream identifier. Ordering is guaranteed within a partition and not within a topic. Directing all events for a given stream to the same partition is what causes commencement, segment and termination events to arrive in that order. It also establishes the ceiling for paragraph 5-4: consumers in excess of the partition count can never be usefully employed, as they are assigned nothing.

5-2.2 Why a single load balancer is not used. The application load balancer interprets HTTP: it reads a hostname, matches a path, terminates encryption. RTMP possesses none of these properties; it is a persistent TCP conversation with its own handshake, and a balancer attempting to interpret it will disrupt it. Ingest therefore receives a network load balancer, which transfers bytes and interprets nothing. This is the clearest instance in the platform of selecting the component that matches the protocol.

5-4. Elastic transcoding

5-4.1 The continuously running worker is replaced by per-stream jobs. A workload autoscaler observes broker consumer lag and creates one job per pending stream; a node autoscaler provisions capacity for those jobs and removes it afterwards.

5-4.2 Consumer lag, being the difference between messages produced and messages processed, is the correct signal. It measures work awaiting attention rather than work in progress, and is materially better than processor utilisation for this purpose.

CAUTION

The scaler shall be capped at the partition count. Consumers beyond that number are assigned no work; they start, remain idle, and are charged. This form of waste presents as successful scaling.

The disposition of a partially completed job shall be decided deliberately. A transcode interrupted mid-stream leaves partial output. Whether that job is retried, and whether retrying produces duplicate segments, is a design decision and shall not be discovered in service.

5-4.3 Spot capacity is appropriate at this paragraph and not elsewhere. These jobs are interruptible and re-runnable, which is the workload for which reclaimable capacity exists.

5-5. Continuous deployment

5-5.1 An agent within the cluster observes the repository and continuously causes the cluster to correspond to it. Deployment commands cease; changes are merged instead.

5-5.2 Pull compared with push. A push pipeline requires the integration system to hold credentials to the production cluster. Every runner, every third-party action and every contributor able to amend a workflow definition then lies within the affected area. A pull agent requires no inbound access; it reaches outward. No cluster credential exists outside the cluster. Because it reconciles continuously rather than at deployment time, a manually amended resource is reverted automatically and the cluster ceases to drift from the repository.

NOTE

Certain components cannot be managed by the agent, including the cluster itself, identity roles and the database, as they shall exist before the agent does. The boundary between agent-managed and separately managed infrastructure shall be recorded. Where this is omitted, two partial accounts of what is deployed result.

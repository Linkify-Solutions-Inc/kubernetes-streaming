Chapter 1 — Introduction

1-1.Purpose. This manual walks you through building, verifying, and tearing down the complete Linkify streaming platform on AWS, from a fresh Ubuntu workstation to a live RTMP stream transcoded and served worldwide — and back to a zero-cost account. Every command in it was executed and verified in a real build on 2026-08-10/11. Where that build hit a defect, this manual either bakes the fix into the repository (you inherit it) or marks the hazard with a box.

1-2.Scope. Your journey starts at your existing AWS identity — the user fatima with the StreamingDeploy permission set, already created for you. Account-level administration (creating users, billing, root actions) is out of scope and out of your permissions; that is by design, not distrust — the same design keeps everyone's blast radius small.

1-3.How to use this manual. Work strictly in order — chapters are sequenced so that everything a step needs already exists. Three habits are mandatory:

  1. Run every CHECKPOINT. A green CHECKPOINT box after a step is not optional ceremony; it is how you find out a silent failure happened now instead of three chapters later. If a checkpoint's expected output doesn't match, stop and consult Appendix A.
  2. Never copy an identifier from an example. Anything shaped like vpc-0b9b…, subnet-…, sg-…, or an ARN with a random suffix was generated for a build that no longer exists. Chapter 4 teaches you to discover your own.
  3. Run commands from the repository root (~/linkify/kubernetes-streaming in this manual). Relative paths like -f infra/eks/cluster.yaml resolve from there.
Warning — real money

From Chapter 5 onward this procedure creates billable AWS resources: ≈ $0.33/hour while the full platform runs (≈ $240/month if forgotten). The teardown in Chapter 12 returns the account to $0 and is part of the procedure, not an afterthought. Never end a working session without either completing teardown or consciously deciding — out loud, to Aayush — that the platform stays up overnight.

Note — when something breaks

Something will break; that is the nature of the exercise. The debugging sequence that solved all 18 defects in the reference build was always the same: read the actual error (kubectl describe, logs, CloudFormation events), locate which layer refused (admission? scheduler? controller? AWS API?), and fix the declaration in git rather than the live object. Appendix A maps every symptom seen in the reference build to its cause.

Chapter 5 — Cluster build

Caution — edit before you build

The file infra/eks/cluster.yaml lists a second administrator under accessEntries so no single deleted identity can lock everyone out. The cluster's creator gets admin automatically, and eksctl fails if the creator also appears in the list. The reference build was created by AdminAccess with StreamingDeploy (you) as second admin. You are the creator now, so the roles swap — put AdminAccess in the list instead:

aws iam list-roles --path-prefix /aws-reserved/sso.amazonaws.com/ \
  --query 'Roles[?contains(RoleName,`AdminAccess`)].Arn' --output text

Replace the principalARN: value in accessEntries with that ARN, then commit and push.

5-1.Create the cluster. One declarative file drives this: VPC, subnets across two pinned availability zones, one NAT gateway, the EKS control plane, access entries, a 4-node system nodegroup, and six add-ons. Expect 15–20 minutes.

cd ~/linkify/kubernetes-streaming
eksctl create cluster -f infra/eks/cluster.yaml
Note — if it fails partway

Do not delete and restart. eksctl builds in units (cluster stack → nodegroup stack → add-ons); completed units stand. Resume the failed unit only: eksctl create nodegroup -f infra/eks/cluster.yaml or eksctl create addon -f infra/eks/cluster.yaml. The reference build recovered from a mid-build failure exactly this way — total loss of work: zero.

Checkpoint 5-A
kubectl get nodes            # 4 nodes, all Ready, no EXTERNAL-IP column values
kubectl get pods -A          # everything Running/Completed
kubectl top nodes            # numbers appear (proves metrics-server)
aws eks list-addons --cluster-name streaming --region us-east-1
# coredns, eks-pod-identity-agent, kube-proxy, vpc-cni, metrics-server, aws-ebs-csi-driver

The final line of eksctl output reads EKS cluster "streaming" in "us-east-1" region is ready and your kubeconfig has been written automatically.

Chapter 6 — Network hardening

6-1.Discover this build's network (your first real use of Chapter 4):

VPC=$(aws ec2 describe-vpcs --filters Name=tag:alpha.eksctl.io/cluster-name,Values=streaming \
  --query 'Vpcs[0].VpcId' --output text)
aws ec2 describe-route-tables --filters Name=vpc-id,Values=$VPC \
  --query 'RouteTables[].[RouteTableId,Tags[?Key==`Name`].Value|[0]]' --output text
aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC \
  --query 'Subnets[].[SubnetId,AvailabilityZone,Tags[?Key==`Name`].Value|[0]]' --output text
CSG=$(aws eks describe-cluster --name streaming \
  --query 'cluster.resourcesVpcConfig.clusterSecurityGroupId' --output text)
echo "VPC=$VPC  CSG=$CSG"

Note the two route tables whose Name contains Private and the two subnets whose Name contains Private — they are used in the next two commands.

6-2.S3 gateway endpoint. Free, and it routes every HLS segment the transcoder writes to S3 around the NAT gateway's $0.045/GB toll — for a streaming platform this is the single biggest cost lever in the design:

aws ec2 create-vpc-endpoint --vpc-id $VPC \
  --service-name com.amazonaws.us-east-1.s3 --vpc-endpoint-type Gateway \
  --route-table-ids <rtb-PrivateA> <rtb-PrivateB> \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=streaming-s3-gateway},{Key=Project,Value=streaming}]'

6-3.Karpenter discovery tags. Karpenter finds where to launch nodes by tag. Without these, node provisioning in Chapter 11 fails silently:

aws ec2 create-tags --resources <subnet-PrivateA> <subnet-PrivateB> $CSG \
  --tags Key=karpenter.sh/discovery,Value=streaming

6-4.Substitute the VPC ID into k8s/platform/aws-load-balancer-controller.yaml (the vpcId: line), commit, push.

Checkpoint 6-A
aws ec2 describe-route-tables --route-table-ids <rtb-PrivateA> <rtb-PrivateB> \
  --query 'RouteTables[].[RouteTableId,Routes[?starts_with(GatewayId,`vpce-`)].GatewayId|[0]]' --output text
# both rows show a vpce- id
aws ec2 describe-tags --filters "Name=key,Values=karpenter.sh/discovery" \
  --query 'Tags[].[ResourceId,ResourceType,Value]' --output text
# exactly: 2 subnets + 1 security-group, all value "streaming"

Chapter 7 — Controller IAM prerequisites

7-1.Load balancer controller. The controller that turns Kubernetes Ingress/Service objects into AWS load balancers needs an IAM policy (published by its project, versioned with the chart — v3.5.0 here must match the chart pin in k8s/platform/aws-load-balancer-controller.yaml) and a service account wired to it:

curl -fsSL -o /tmp/lbc-iam-policy.json \
  https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v3.5.0/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file:///tmp/lbc-iam-policy.json
eksctl create iamserviceaccount --cluster streaming --region us-east-1 \
  --namespace kube-system --name aws-load-balancer-controller \
  --attach-policy-arn arn:aws:iam::242626138899:policy/AWSLoadBalancerControllerIAMPolicy --approve

7-2.Karpenter. The node autoscaler needs a node role, controller policies, and an interruption queue — all from its official CloudFormation template (version must match the chart pin, 1.13.0), then a service account with the six policies the template creates, then cluster access for the node role:

curl -fsSL -o /tmp/karpenter-cfn.yaml \
  https://raw.githubusercontent.com/aws/karpenter-provider-aws/v1.13.0/website/content/en/docs/getting-started/getting-started-with-karpenter/cloudformation.yaml
aws cloudformation deploy --stack-name Karpenter-streaming \
  --template-file /tmp/karpenter-cfn.yaml \
  --capabilities CAPABILITY_NAMED_IAM --parameter-overrides ClusterName=streaming --region us-east-1

# collect the six controller policy ARNs the stack created
aws iam list-policies --scope Local \
  --query 'Policies[?contains(PolicyName,`Karpenter`)].Arn' --output text

eksctl create iamserviceaccount --cluster streaming --region us-east-1 \
  --namespace kube-system --name karpenter \
  --attach-policy-arn <arn-1> --attach-policy-arn <arn-2> --attach-policy-arn <arn-3> \
  --attach-policy-arn <arn-4> --attach-policy-arn <arn-5> --attach-policy-arn <arn-6> \

Chapter 8 — Data layer

8-1.RDS Postgres (start first — it takes ~10 minutes; continue with 8-2 while it creates). Uses the private subnets and cluster security group discovered in Chapter 6:

aws rds create-db-subnet-group --db-subnet-group-name streaming-db-subnets \
  --db-subnet-group-description "streaming: private subnets" \
  --subnet-ids <subnet-PrivateA> <subnet-PrivateB>

DBSG=$(aws ec2 create-security-group --group-name streaming-db \
  --description "RDS postgres: 5432 from cluster SG only" --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $DBSG --protocol tcp --port 5432 --source-group $CSG

aws rds create-db-instance --db-instance-identifier streaming-db \
  --db-instance-class db.t4g.micro --engine postgres --engine-version 16.11 \
  --allocated-storage 20 --storage-type gp3 --storage-encrypted \
  --master-username streaming_admin --manage-master-user-password \
  --db-name streaming --vpc-security-group-ids $DBSG \
  --db-subnet-group-name streaming-db-subnets --no-publicly-accessible \
  --backup-retention-period 1 --no-multi-az --tags Key=Project,Value=streaming
Note

--manage-master-user-password makes AWS generate, store, and rotate the database password in Secrets Manager. No human ever sees it; the cluster reads it via External Secrets. If engine version 16.11 is retired by the time you run this, list what exists and take the newest 16.x: aws rds describe-db-engine-versions --engine postgres --query 'DBEngineVersions[].EngineVersion' --output text

Chapter 9 — DNS & TLS (coordinated step)

9-1.Create the zone and certificate. The platform's public names live under k8s.linkifysolutions.com. You create the Route53 zone and request a wildcard certificate; validation is automatic once the parent domain delegates to your zone:

ZID=$(aws route53 create-hosted-zone --name k8s.linkifysolutions.com \
  --caller-reference streaming-$RANDOM$RANDOM --query 'HostedZone.Id' --output text)
aws route53 get-hosted-zone --id $ZID --query 'DelegationSet.NameServers' --output text | tr '\t' '\n'
# ^ FOUR nameserver hostnames — send these to Aayush (9-2)

CERT=$(aws acm request-certificate --domain-name "*.k8s.linkifysolutions.com" \
  --subject-alternative-names k8s.linkifysolutions.com --validation-method DNS \
  --query CertificateArn --output text)
sleep 15
aws acm describe-certificate --certificate-arn $CERT \
  --query 'Certificate.DomainValidationOptions[0].ResourceRecord.[Name,Value]' --output text
# put that CNAME into your zone (substitute the Name and Value you just got):
aws route53 change-resource-record-sets --hosted-zone-id $ZID --change-batch '{
  "Changes":[{"Action":"UPSERT","ResourceRecordSet":{
    "Name":"<validation-record-Name>","Type":"CNAME","TTL":300,
    "ResourceRecords":[{"Value":"<validation-record-Value>"}]}}]}'
Caution — Aayush performs this part

The parent domain linkifysolutions.com is hosted on Cloudflare, which you do not have access to. Send Aayush the four nameserver hostnames. He adds four NS records in Cloudflare — each named k8s, one per value, proxy OFF ("DNS only"). Until this happens the certificate stays PENDING_VALIDATION and the web Ingress cannot come up; everything else in this manual proceeds regardless.

9-2.Substitute the certificate ARN into k8s/apps/overlays/prod/ingress-alb.yaml (Chapter 4 registry), commit, push. Later, when delegation is live, confirm issuance: aws acm describe-certificate --certificate-arn $CERT --query 'Certificate.Status' → ISSUED.

Note — the cold-start trade

The first ~77 seconds of a brand-new stream are not in the HLS output — that's the scale-from-zero price. Viewers of an already-running stream never notice. Eliminating it means paying for an idle warm node around the clock. Question worth pondering during the wait: at what stream frequency does the warm node become the cheaper option?

Chapter 12 — Teardown

12-1.Phase A — in-cluster (ordering is load-bearing; the reference build derived each rule the hard way — see the header of scripts/teardown.sh for the full annotated sequence):

  1. Disarm the root app's self-healing so deletions stick:
    kubectl patch application root -n argocd --type merge -p '{"spec":{"syncPolicy":{"automated":null}}}'
  2. Delete the load-balancer-owning apps while the LB controller still lives:
    kubectl delete application streaming mediamtx -n argocd
    Verify: aws elbv2 describe-load-balancers returns an empty list before continuing.
  3. Delete CR consumers before their operators (else finalizers wedge namespaces):
    kubectl delete application kafka db-migrate secrets karpenter-pools -n argocd
  4. Delete everything else, explicitly:
    kubectl delete application root -n argocd; kubectl delete applications --all -n argocd
    Wait until kubectl get applications -n argocd is empty and kubectl get pvc -A is empty.
  5. helm uninstall argocd -n argocd, then delete leftover namespaces:
    kubectl delete ns argocd external-secrets karpenter keda monitoring
Note — two known wedges

Namespace stuck Terminating, reason DiscoveryFailed: a dead aggregated API poisons discovery. kubectl get apiservices | awk '$3=="False"' → delete the dead one (typically v1beta1.external.metrics.k8s.io).
KafkaTopics refuse deletion: their operator died first. kubectl patch kafkatopic <name> -n kafka --type merge -p '{"metadata":{"finalizers":null}}'

12-2.Phase B — AWS side. One script, discovery-based, ~25–35 minutes, ends by printing the zero-cost verification (every list empty):

AWS_PROFILE=streaming-deploy bash scripts/teardown.sh
Checkpoint 12-A — the account is empty

The script's final section prints CloudFormation stacks, EC2 instances, load balancers, EBS volumes, VPCs, NAT gateways, and RDS instances. Every one must be empty. Anything left is money leaking — hunt it down before you stop. Finally, tell Aayush to remove the four k8s NS records from Cloudflare.

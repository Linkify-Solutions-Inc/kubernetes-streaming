Chapter 1 — Introduction

1-1.Purpose. This manual walks you through building, verifying, and tearing down the complete Linkify streaming platform on AWS, from a fresh Ubuntu workstation to a live RTMP stream transcoded and served worldwide — and back to a zero-cost account. Every command in it was executed and verified in a real build on 2026-08-10/11. Where that build hit a defect, this manual either bakes the fix into the repository (you inherit it) or marks the hazard with a box.

1-2.Scope. Your journey starts at your existing AWS identity — the user fatima with the StreamingDeploy permission set, already created for you. Account-level administration (creating users, billing, root actions) is out of scope and out of your permissions; that is by design, not distrust — the same design keeps everyone's blast radius small.

1-3.How to use this manual. Work strictly in order — chapters are sequenced so that everything a step needs already exists. Three habits are mandatory:

  1. Run every CHECKPOINT. A green CHECKPOINT box after a step is not optional ceremony; it is how you find out a silent failure happened now instead of three chapters later. If a checkpoint's expected output doesn't match, stop and consult Appendix A.
  2. Never copy an identifier from an example. Anything shaped like vpc-0b9b…, subnet-…, sg-…, or an ARN with a random suffix was generated for a build that no longer exists. Chapter 4 teaches you to discover your own.
  3. Run commands from the repository root (~/linkify/kubernetes-streaming in this manual). Relative paths like -f infra/eks/cluster.yaml resolve from there.
Warning — real money

From Chapter 5 onward this procedure creates billable AWS resources: ≈ $0.33/hour while the full platform runs (≈ $240/month if forgotten). The teardown in Chapter 12 returns the account to $0 and is part of the procedure, not an afterthought. Never end a working session without either completing teardown or consciously deciding — out loud, to Aayush — that the platform stays up overnight.

Note — when something breaks

Something will break; that is the nature of the exercise. The debugging sequence that solved all 18 defects in the reference build was always the same: read the actual error (kubectl describe, logs, CloudFormation events), locate which layer refused (admission? scheduler? controller? AWS API?), and fix the declaration in git rather than the live object. Appendix A maps every symptom seen in the reference build to its cause.

Command anatomy — what each tool actually is
aws
A signed-HTTP client for every AWS API. Each subcommand family (ec2, rds, s3api…) maps 1:1 to a service's API; nothing is magic, everything is a request you could have made with curl and a signature.
eksctl
A cluster compiler: reads cluster.yaml, emits CloudFormation stacks, waits on them. It keeps no state of its own — the file plus the stacks are the state.
kubectl
The Kubernetes API client. Everything it does — get, apply, delete, logs, port-forward — is an HTTPS call to the cluster's API server, authenticated via your AWS identity.
helm
A package manager for Kubernetes: a "chart" is templated YAML plus defaults; install renders it with your values and applies the result as one tracked release.
ffmpeg
The Swiss-army knife of audio/video. Here it plays two roles: your fake OBS (Chapter 11) and, inside the transcode image, the real encoder.
Note — WSL2 is fine

If your Ubuntu is WSL2 on Windows, run everything in this manual inside the WSL terminal, unchanged. Two things to know: kubectl port-forward tunnels a pod in AWS to localhost — nothing runs on your machine, the terminal is just holding a doorway open — and WSL2 forwards localhost to Windows by default, so Grafana at http://localhost:3000 opens in your normal Windows browser. Only ffmpeg (Chapter 11) does real local work: it plays the streamer, pushing video over the internet like OBS would.

Command anatomy — SSO login mechanics

aws configure sso writes two blocks to ~/.aws/config — a profile (account + role) and an sso-session (where to log in) — and nothing secret. aws sso login runs a browser device-flow: you authenticate (password + MFA), AWS hands the CLI a short-lived token, and every later command silently exchanges it for role credentials. The ARN in Checkpoint 3-A reads assumed-role/<role>/<you> — you are never "a user with keys", you are a person temporarily wearing a role. Expiry after 8 h shows up as sudden auth errors; the fix is always just aws sso login again.

Checkpoint 3-A

The Arn ends in assumed-role/AWSReservedSSO_StreamingDeploy_<hash>/fatima. If it shows anything else, you are the wrong identity — stop.

Note — the Identity Center region

Identity Center for this account lives in us-east-1, same as the workloads, and the SSO role ARNs therefore have no region segment in their path. If you ever see documentation showing …/us-east-2/AWSReservedSSO_… paths, that describes a different account layout — not a bug to fix, just a difference to ignore.

Chapter 4 — Identifier discovery doctrine

4-1.The rule. AWS generates a fresh ID for every resource it creates. The build this manual is based on was completely destroyed; when you rebuild, every generated ID will differ. Identifiers split into exactly two classes:

ClassExamplesYour action
Stable (account-scoped names) account 242626138899 · start URL d-90667b4413.awsapps.com/start · policy names like streaming-eso · bucket linkify-streaming-media-242626138899 Use as printed; already correct inside the repository.
Generated (per-build) vpc-…, subnet-…, rtb-…, sg-…, vpce-…, RDS endpoint & master-secret name, ACM certificate ARN, load-balancer hostnames, CloudFront domain Discover with the command given at point of use; substitute into the file named there.

4-2.Substitution registry. Only three repository files carry generated IDs. Each marks the spot with a REBUILD-SENSITIVE comment containing its own discovery command — the file teaches you even if you lose this manual:

FileValueDiscovery command
k8s/platform/aws-load-balancer-controller.yamlvpcId aws ec2 describe-vpcs --filters Name=tag:alpha.eksctl.io/cluster-name,Values=streaming --query 'Vpcs[0].VpcId' --output text
k8s/infra/secrets/externalsecret-db.yamlRDS master-secret name (rds!db-…) aws rds describe-db-instances --db-instance-identifier streaming-db --query 'DBInstances[0].MasterUserSecret.SecretArn' --output text — use the NAME portion (strip the trailing -XXXXXX)
k8s/apps/overlays/prod/ingress-alb.yamlACM certificate ARN aws acm list-certificates --query 'CertificateSummaryList[?DomainName==`*.k8s.linkifysolutions.com`].CertificateArn' --output text

After each substitution: git add -A && git commit -m "substitute <what> for this build" && git push. The GitOps engine (Chapter 10) reads GitHub, not your working tree — an unpushed fix does not exist.

Command anatomy — reading the discovery commands (--query / --filters / --output)

Every discovery command uses the same three levers, worth learning once:

--filters Name=…,Values=…
Server-side narrowing — AWS returns only matching resources (e.g. the VPC carrying our cluster tag).
--query '…'
Client-side reshaping in JMESPath: Vpcs[0].VpcId = first element's field; Roles[?contains(RoleName,`AdminAccess`)].Arn = filter-then-project; [] flattens. Backticks quote literals.
--output text|table|json
text for values you'll paste or pipe, table for human eyes, default JSON for everything else.

Nothing about these flags changes what exists — discovery is always read-only, which is why you can rerun any of it freely.

Chapter 5 — Cluster build

Caution — check the access entry BEFORE you build

The file infra/eks/cluster.yaml lists a second administrator under accessEntries so no single deleted identity can lock everyone out. The cluster's creator gets admin automatically (bootstrapClusterCreatorAdminPermissions), and eksctl refuses to also list the creator in accessEntries. The correct entry therefore depends on who creates the cluster — find out first, do not guess:

  1. Your creator role is the one in your aws sts get-caller-identity Arn (Checkpoint 3-A). Run it.
  2. Creator is AdminAccess (profile streaming-admin): the file is already correct — StreamingDeploy is the second admin. Do not edit anything. Creating with the file as-committed is verified to work.
  3. Creator is StreamingDeploy (profile streaming-deploy): you are the listed second admin, so you must swap the entry to the other admin. Run exactly, then paste the printed ARN into principalARN::
aws iam list-roles --path-prefix /aws-reserved/sso.amazonaws.com/ \
  --query 'Roles[?contains(RoleName,`AdminAccess`)].Arn' --output text
# expect: arn:aws:iam::242626138899:role/aws-reserved/sso.amazonaws.com/AWSReservedSSO_AdminAccess_<hash>

Verify your paste before building. The value must be a role ARN, never your assumed-role session ARN (the trap Chapter 4 calls out). A wrong ARN fails the access-entry step with an error naming the principal ARN. Sanity-check it, then commit and push (an unpushed edit does not exist):

echo '<the ARN you pasted>' | grep -q 'role/aws-reserved/sso.amazonaws.com/' && echo OK || echo BAD
git add infra/eks/cluster.yaml && git commit -m "cluster: swap second admin for StreamingDeploy creator" && git push origin master

5-1.Create the cluster. One declarative file drives this: VPC, subnets across two pinned availability zones, one NAT gateway, the EKS control plane, access entries, a 4-node system nodegroup, and six add-ons. Expect 15–20 minutes.

cd ~/linkify/kubernetes-streaming
eksctl create cluster -f infra/eks/cluster.yaml
Command anatomy — what eksctl is doing for those 20 minutes

Two CloudFormation stacks. eksctl-streaming-cluster: the VPC (subnets, route tables, one NAT, internet gateway), the EKS control plane (AWS-managed apiserver+etcd — the $0.10/hr), the OIDC provider, access entries, and the six add-ons. Then eksctl-streaming-nodegroup-system: a launch template + auto-scaling group that boots four EC2 machines which join the cluster. Progress is visible as stack events in the CloudFormation console — when eksctl "hangs", it is politely waiting on a stack, and the console names the resource it's waiting for. It finishes by writing ~/.kube/config: the cluster's address plus an instruction to authenticate via your AWS identity — no separate Kubernetes password exists.

Note — if it fails partway

Do not delete and restart. eksctl builds in units (cluster stack → nodegroup stack → add-ons); completed units stand. Resume the failed unit only: eksctl create nodegroup -f infra/eks/cluster.yaml or eksctl create addon -f infra/eks/cluster.yaml. The reference build recovered from a mid-build failure exactly this way — total loss of work: zero.

Checkpoint 5-A
kubectl get nodes            # 4 nodes, all Ready, no EXTERNAL-IP column values
kubectl get pods -A          # everything Running/Completed
kubectl top nodes            # numbers appear (proves metrics-server)
aws eks list-addons --cluster-name streaming --region us-east-1
# coredns, eks-pod-identity-agent, kube-proxy, vpc-cni, metrics-server, aws-ebs-csi-driver

The final line of eksctl output reads EKS cluster "streaming" in "us-east-1" region is ready and your kubeconfig has been written automatically.

Chapter 6 — Network hardening

6-1.Discover this build's network (your first real use of Chapter 4):

VPC=$(aws ec2 describe-vpcs --filters Name=tag:alpha.eksctl.io/cluster-name,Values=streaming \
  --query 'Vpcs[0].VpcId' --output text)
aws ec2 describe-route-tables --filters Name=vpc-id,Values=$VPC \
  --query 'RouteTables[].[RouteTableId,Tags[?Key==`Name`].Value|[0]]' --output text
aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC \
  --query 'Subnets[].[SubnetId,AvailabilityZone,Tags[?Key==`Name`].Value|[0]]' --output text
CSG=$(aws eks describe-cluster --name streaming \
  --query 'cluster.resourcesVpcConfig.clusterSecurityGroupId' --output text)
echo "VPC=$VPC  CSG=$CSG"

Note the two route tables whose Name contains Private and the two subnets whose Name contains Private — they are used in the next two commands.

6-2.S3 gateway endpoint. Free, and it routes every HLS segment the transcoder writes to S3 around the NAT gateway's $0.045/GB toll — for a streaming platform this is the single biggest cost lever in the design:

aws ec2 create-vpc-endpoint --vpc-id $VPC \
  --service-name com.amazonaws.us-east-1.s3 --vpc-endpoint-type Gateway \
  --route-table-ids <rtb-PrivateA> <rtb-PrivateB> \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=streaming-s3-gateway},{Key=Project,Value=streaming}]'

6-3.Karpenter discovery tags. Karpenter finds where to launch nodes by tag. Without these, node provisioning in Chapter 11 fails silently:

aws ec2 create-tags --resources <subnet-PrivateA> <subnet-PrivateB> $CSG \
  --tags Key=karpenter.sh/discovery,Value=streaming
Command anatomy — gateway endpoints and tags

A gateway VPC endpoint is a routing trick, not a server: AWS injects a route into the named route tables sending S3-bound traffic (matched by a managed prefix list) across AWS's backbone instead of out the NAT gateway. Free, invisible to applications, no throughput to size — which is why it's the rare optimization with no trade-off. (Its cousin, the interface endpoint, is a billable ENI — not what we use.) create-tags attaches plain key/value metadata; tags do nothing by themselves, but Karpenter searches by them — tagging is how you leave signposts for controllers that arrive later.

6-4.Substitute the VPC ID into k8s/platform/aws-load-balancer-controller.yaml (the vpcId: line), commit, push.

Checkpoint 6-A
aws ec2 describe-route-tables --route-table-ids <rtb-PrivateA> <rtb-PrivateB> \
  --query 'RouteTables[].[RouteTableId,Routes[?starts_with(GatewayId,`vpce-`)].GatewayId|[0]]' --output text
# both rows show a vpce- id
aws ec2 describe-tags --filters "Name=key,Values=karpenter.sh/discovery" \
  --query 'Tags[].[ResourceId,ResourceType,Value]' --output text
# exactly: 2 subnets + 1 security-group, all value "streaming"

  --attach-policy-arn <arn-1> --attach-policy-arn <arn-2> --attach-policy-arn <arn-3> \
  --attach-policy-arn <arn-4> --attach-policy-arn <arn-5> --attach-policy-arn <arn-6> \
  --approve

  --principal-arn arn:aws:iam::242626138899:role/KarpenterNodeRole-streaming --type EC2_LINUX
Command anatomy — the IAM machinery in this chapter
aws iam create-policy
Uploads a JSON permission document as a named, versioned object. Creating it grants nothing — policies are inert until attached to a role.
eksctl create iamserviceaccount
One command, three artifacts (via a small CFN stack): an IAM role whose trust policy accepts tokens from this cluster's OIDC provider for this exact namespace/name; the policy attachment; and the Kubernetes ServiceAccount annotated with the role ARN. That is IRSA end-to-end — pods using the SA exchange their service-account token for AWS credentials, keylessly.
aws cloudformation deploy
Create-or-update with changesets: safe to rerun; shows "no changes" when the stack matches. --capabilities CAPABILITY_NAMED_IAM is you acknowledging the template creates named IAM resources.
aws eks create-access-entry --type EC2_LINUX
Tells the cluster "EC2 instances presenting this role are worker nodes" — the API-mode replacement for the old aws-auth ConfigMap edit. Without it, Karpenter's machines would boot, try to join, and be politely refused.
Checkpoint 7-A
kubectl get sa aws-load-balancer-controller karpenter -n kube-system \

Chapter 8 — Data layer

8-1.RDS Postgres (start first — it takes ~10 minutes; continue with 8-2 while it creates). Uses the private subnets and cluster security group discovered in Chapter 6:

aws rds create-db-subnet-group --db-subnet-group-name streaming-db-subnets \
  --db-subnet-group-description "streaming: private subnets" \
  --subnet-ids <subnet-PrivateA> <subnet-PrivateB>

DBSG=$(aws ec2 create-security-group --group-name streaming-db \
  --description "RDS postgres: 5432 from cluster SG only" --vpc-id $VPC --query GroupId --output text)
aws ec2 authorize-security-group-ingress --group-id $DBSG --protocol tcp --port 5432 --source-group $CSG

aws rds create-db-instance --db-instance-identifier streaming-db \
  --db-instance-class db.t4g.micro --engine postgres --engine-version 16.11 \
  --allocated-storage 20 --storage-type gp3 --storage-encrypted \
  --master-username streaming_admin --manage-master-user-password \
  --db-name streaming --vpc-security-group-ids $DBSG \
  --db-subnet-group-name streaming-db-subnets --no-publicly-accessible \
  --backup-retention-period 1 --no-multi-az --tags Key=Project,Value=streaming
Command anatomy — create-db-instance, flag by flag
subnet group + --no-publicly-accessible
Pins the database inside the private subnets with no public IP; the only path in is port 5432 from the cluster security group (the SG-to-SG rule above — membership-based, no IP lists to maintain).
--engine-version / db.t4g.micro / gp3 / 20 GB
Smallest sensible Postgres: ARM instance (~$0.017/hr), general-purpose SSD at free-tier IOPS.
--manage-master-user-password
The star flag: AWS generates the password, stores it in Secrets Manager under a name it chooses (your Chapter 4 substitution), and can rotate it. No human ever knows it; ESO delivers it to pods; rotation needs no redeploy.
--storage-encrypted / --backup-retention-period 1 / --no-multi-az
Encryption at rest is table stakes; one day of backups and a single AZ are learning-platform economics — production would raise both.
Note

--manage-master-user-password makes AWS generate, store, and rotate the database password in Secrets Manager. No human ever sees it; the cluster reads it via External Secrets. If engine version 16.11 is retired by the time you run this, list what exists and take the newest 16.x: aws rds describe-db-engine-versions --engine postgres --query 'DBEngineVersions[].EngineVersion' --output text

8-2.S3 media bucket.

B=linkify-streaming-media-242626138899
aws s3api create-bucket --bucket $B

  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

Command anatomy — the four s3api calls
create-bucket
Bucket names are globally unique across all AWS customers — hence the account-id suffix.
put-public-access-block
Four switches that make public exposure structurally impossible regardless of any future policy mistake. Viewers never touch S3 directly — CloudFront does.
put-bucket-lifecycle-configuration
One rule: abandoned multipart uploads (a crashed upload's invisible half-transferred parts, which bill as storage) get reaped after 7 days.
put-bucket-cors
Lets browsers on other origins GET segments — required because the player page and the CDN are different hostnames. GET/HEAD only; nobody writes via CORS.

At runtime the Pod Identity agent (one of the Chapter 5 add-ons) intercepts the SDK's credential lookup inside any pod running as that service account and serves short-lived role credentials. Compare with IRSA (Chapter 7): same outcome, but the binding lives on the AWS side keyed by names — which is why renaming a ServiceAccount silently unbinds it.

Note — why ListBucket is unconditioned

The reference build first scoped upload-api's s3:ListBucket with a raw/* prefix condition. Its own readiness probe then failed with 403: the probe calls HeadBucket, which performs an unprefixed ListBucket check. The policy above is the corrected version. Lesson: an app's health checks are part of its permission surface.

Chapter 9 — DNS & TLS (coordinated step)

9-1.Create the zone and certificate. The platform's public names live under k8s.linkifysolutions.com. You create the Route53 zone and request a wildcard certificate; validation is automatic once the parent domain delegates to your zone:

ZID=$(aws route53 create-hosted-zone --name k8s.linkifysolutions.com \
  --caller-reference streaming-$RANDOM$RANDOM --query 'HostedZone.Id' --output text)
aws route53 get-hosted-zone --id $ZID --query 'DelegationSet.NameServers' --output text | tr '\t' '\n'
# ^ FOUR nameserver hostnames — send these to Aayush (9-2)

CERT=$(aws acm request-certificate --domain-name "*.k8s.linkifysolutions.com" \
  --subject-alternative-names k8s.linkifysolutions.com --validation-method DNS \
  --query CertificateArn --output text)
sleep 15
aws acm describe-certificate --certificate-arn $CERT \
  --query 'Certificate.DomainValidationOptions[0].ResourceRecord.[Name,Value]' --output text
# put that CNAME into your zone (substitute the Name and Value you just got):
aws route53 change-resource-record-sets --hosted-zone-id $ZID --change-batch '{
  "Changes":[{"Action":"UPSERT","ResourceRecordSet":{
    "Name":"<validation-record-Name>","Type":"CNAME","TTL":300,
    "ResourceRecords":[{"Value":"<validation-record-Value>"}]}}]}'
Command anatomy — zones, delegation, and DNS-validated certificates

A Route53 hosted zone is an authoritative database for one subtree of the DNS. Creating it assigns four AWS nameservers — but the world doesn't know they're in charge until the parent zone (Cloudflare's linkifysolutions.com) publishes NS records pointing k8s at them. That pointer is the delegation, and it is the entire reason Aayush's step exists. ACM's DNS validation is a proof-of-control loop: it gives you a random CNAME only the zone's controller could publish; you publish it (change-resource-record-sets with UPSERT — create-or-overwrite, idempotent); once the delegation makes it publicly resolvable, ACM issues. The certificate then renews itself forever as long as the record stays.

Caution — Aayush performs this part

The parent domain linkifysolutions.com is hosted on Cloudflare, which you do not have access to. Send Aayush the four nameserver hostnames. He adds four NS records in Cloudflare — each named k8s, one per value, proxy OFF ("DNS only"). Until this happens the certificate stays PENDING_VALIDATION and the web Ingress cannot come up; everything else in this manual proceeds regardless.

9-2.Substitute the certificate ARN into k8s/apps/overlays/prod/ingress-alb.yaml (Chapter 4 registry), commit, push. Later, when delegation is live, confirm issuance: aws acm describe-certificate --certificate-arn $CERT --query 'Certificate.Status' → ISSUED.

Command anatomy — the ffmpeg incantation
-re
Real-time pacing — feed frames at playback speed like a camera, not as fast as the CPU allows. Without it you'd "stream" 7 minutes of video in 20 seconds.
-f lavfi -i testsrc… / sine…
Synthetic video (a moving test pattern) and a 440 Hz tone — a camera and microphone made of math.
-c:v libx264 -b:v 2500k -g 60
H.264 at 2.5 Mbps; a keyframe every 60 frames (2 s at 30 fps) — segment boundaries can only fall on keyframes, so this bounds HLS segment timing.
-c:a aac / -f flv / rtmp://
AAC audio in an FLV container, because RTMP — a 2002 protocol that simply refuses to die — carries only FLV. The path component is your stream key: possession of it is authentication, which is why it never appears in viewer-facing URLs.

Chapter 12 — Teardown

12-1.One command does everything. The script runs both phases — in-cluster first (automatically, when kubectl can reach the cluster), then AWS-side — with self-healing retries for every blocker the reference teardown hit:

AWS_PROFILE=streaming-deploy bash scripts/teardown.sh

12-2.What Phase A does, and why the order is load-bearing (you are not required to run these by hand — read them to understand what the script is doing):

  1. Disarm the root app's self-healing so deletions stick:
    kubectl patch application root -n argocd --type merge -p '{"spec":{"syncPolicy":{"automated":null}}}'
  2. Delete the load-balancer-owning apps while the LB controller still lives:
    kubectl delete application streaming mediamtx -n argocd
    Verify: aws elbv2 describe-load-balancers returns an empty list before continuing.
  3. Delete CR consumers before their operators (else finalizers wedge namespaces):
    kubectl delete application kafka db-migrate secrets karpenter-pools -n argocd
  4. Delete everything else, explicitly:
    kubectl delete application root -n argocd; kubectl delete applications --all -n argocd
    Wait until kubectl get applications -n argocd is empty and kubectl get pvc -A is empty.
  5. helm uninstall argocd -n argocd, then delete leftover namespaces:
    kubectl delete ns argocd external-secrets karpenter keda monitoring
Note — two known wedges

Namespace stuck Terminating, reason DiscoveryFailed: a dead aggregated API poisons discovery. kubectl get apiservices | awk '$3=="False"' → delete the dead one (typically v1beta1.external.metrics.k8s.io).
KafkaTopics refuse deletion: their operator died first. kubectl patch kafkatopic <name> -n kafka --type merge -p '{"metadata":{"finalizers":null}}'

12-3.Phase B then unwinds the AWS side (~25–35 minutes; CloudFront and eksctl dominate), self-healing the two known blockers — security groups left in the VPC, and the NAT's orphaned Elastic IP — before printing the zero-cost verification (every list must be empty, including Elastic IPs).

Checkpoint 12-A — the account is empty

The script's final section prints CloudFormation stacks, EC2 instances, load balancers, EBS volumes, VPCs, NAT gateways, and RDS instances. Every one must be empty. Anything left is money leaking — hunt it down before you stop. Finally, tell Aayush to remove the four k8s NS records from Cloudflare.

A home‑grown Twitch, explained in plain English, and where Kubernetes takes it next.

This repo lets anyone go live from OBS or upload a video file, and lets anyone else watch it, no accounts, just a per‑streamer stream key. Under the hood it's five small Python services stitched together with Kafka, ffmpeg, Postgres and S3‑compatible storage. This guide walks through how a byte of video actually gets from a webcam to a browser, and then goes deep on the part you asked about most: what Kubernetes changes, and which of its features are the ones that actually help this system scale.

Nine moving parts, each with one job

Nothing here is one giant app. It's small single‑purpose services that only know about each other through Kafka messages or a database row. Click any "technical detail" to see what's actually happening in the code.

infra

MediaMTX

The loading dock. It's the only thing that speaks "RTMP" (the protocol OBS uses to push a live video feed to a server).

Technical detail

Runs as its own container, listening on port 1935. Before it accepts a publish, it calls out to ingest-webhook's /hooks/auth over HTTP to check the stream key is real. Once a stream is live/dead, it fires runOnReady / runOnNotReady hooks (not "onPublish", a common but wrong assumption carried over from other RTMP servers).

Without it: every service that wanted a live video feed would need to implement RTMP's handshake and chunking itself. One dedicated ingest point means nothing else in the system ever has to know RTMP exists.

service

ingest-webhook

The bouncer. Checks the stream key is on the list before anyone's allowed to go live, then records that a stream started or ended.

Technical detail

FastAPI service. /hooks/auth rejects unknown stream keys with a 401 before MediaMTX accepts the publish. /hooks/publish and /hooks/unpublish fire afterwards: they insert/update a row in the streams table and emit a stream.lifecycle event onto Kafka (started / ended).

Without it: MediaMTX would accept a publish from anyone who knew the RTMP address, no stream-key check at all, so any anonymous connection could go live under someone else's slot or flood the system with junk streams.

service

upload-api

The front desk. Hands out stream keys, lists what's live or uploaded, and takes video files off people's hands.

Technical detail

FastAPI service backed by Postgres + MinIO. POST /streamers mints a stream key. POST /videos streams the upload straight into MinIO under raw/<uuid>, writes a videos row, and emits an upload.events message. GET /streams / GET /videos back the homepage.

Without it: there'd be no single place issuing stream keys or fronting uploads, so every other service would need its own copy of "is this a real streamer" logic, duplicated and easy to get subtly wrong in one of them.

backbone

Kafka

The nervous system. Instead of services calling each other directly, they drop a note on a shared board and whoever cares about that kind of note picks it up.

Technical detail

Single-broker KRaft-mode cluster (no Zookeeper). Five topics, each partitioned by stream/video ID so events for the same stream stay strictly ordered even as partition count grows. See the dedicated section below.

Without it: every service would have to call every other one directly, for example ingest-webhook hitting transcode-worker's API by hand. A slow or crashed transcode-worker would then make ingest-webhook itself hang or fail, instead of the event just waiting safely on a topic until its consumer comes back.

worker

transcode-worker

The video processing factory floor. Takes one raw feed in, and produces three quality levels out, using ffmpeg.

Technical detail

Consumes stream.lifecycle and upload.events directly (no separate dispatcher stage). For a live stream it launches one long-running ffmpeg subprocess per stream and a background thread that uploads new HLS segments to MinIO every 2 seconds. For an upload it downloads the raw file, runs ffmpeg once, and pushes the finished HLS folder to storage. Currently one process juggles every concurrent stream via Python threads. See the Kubernetes section for why that's the most interesting scaling question in this whole system.

Without it: a viewer's player switching from 720p to 480p mid-stream would land on a misaligned keyframe boundary (if the renditions weren't produced from one aligned decode), causing a visible stutter or a frozen frame at every quality switch instead of a clean handoff.

storage

MinIO / S3

The warehouse. Holds the raw uploaded files and the finished video segments, addressed the exact same way whether it's a laptop or AWS.

Technical detail

MinIO in dev speaks the S3 API, so the exact same boto3 client code runs unchanged against real S3 in prod. The media/hls prefix is set public-read so a browser (or VLC) can fetch master.m3u8 directly: a deliberate dev-only convenience.

Without it: video would have to be served by an app server instead of a plain object store, so viewer count would directly load whatever produced the video. A viral stream with ten thousand viewers would mean ten thousand connections into the transcoding process itself, instead of ten thousand cheap, stateless HTTP GETs against storage.

ledger

Postgres

The filing cabinet. Who's a streamer, which streams/videos exist, and a raw log of every "watch" click.

Technical detail

Four tables: streamers, streams, videos, view_events. View counts aren't a running counter column. They're computed with GROUP BY over the raw event log on every read, so the log stays the single source of truth.

Without it: there'd be no durable, queryable record of who's a streamer, what's live, or what's been uploaded. And without the raw log specifically (versus a running counter), a crash mid-update could silently under- or over-count views, with no way to recompute the true number afterward.

worker

analytics-worker

The counting clerk. Watches for "someone hit play" notes and tallies them into the filing cabinet.

Technical detail

Consumes viewer.analytics and inserts a view_events row per view. Also consumes transcode.status but only logs it today: no aggregation needed there yet since transcode-worker already updates videos.status directly.

Without it: view-recording would have to happen synchronously inside upload-api's own request handler, so a burst of viewers all clicking play at once would hammer Postgres directly and could slow the page down for everyone. Buffering through Kafka absorbs that burst instead of passing it straight through.

frontend

web

The storefront and the TV. Browse what's live or uploaded, get a stream key, upload a file, and actually watch things play.

Technical detail

Server-rendered FastAPI + Jinja templates, no SPA framework. /watch/<type>/<id> records a view then plays the MinIO-hosted HLS manifest with hls.js (falling back to native HLS on Safari).

Without it: viewers would need to hand-construct HLS manifest URLs with no browse or discovery page at all, and non-Safari browsers wouldn't play HLS in the first place without the hls.js shim.

Two journeys: going live, and uploading a file

Same destination (a watchable video), two very different starting points. Toggle between them.

1
Streamer → MediaMTX

OBS pushes an RTMP feed

The streamer points OBS at the server's RTMP address with their private stream key as the "path." MediaMTX receives the connection but doesn't accept it yet.

2
MediaMTX → ingest-webhook

The bouncer checks the list

Before accepting the publish, MediaMTX calls /hooks/auth with the stream key. If it's not a real streamer's key, the connection is rejected with a 401: this is the actual security gate.

3
ingest-webhook → Postgres + Kafka

The stream is recorded and announced

A new row lands in streams (status live), and a stream.lifecycle: started event is dropped on Kafka, including the new, public-safe stream_id, never the secret stream key.

4
transcode-worker

ffmpeg spins up, live

Hearing the "started" event, transcode-worker launches a single ffmpeg process that pulls the RTMP feed and simultaneously encodes it into 1080p / 720p / 480p HLS renditions, uploading new 4‑second segments to storage roughly every 2 seconds.

5
Viewer → web → MinIO

A viewer hits play

The homepage lists the stream (with a live view count). Clicking it records a view and loads hls.js, pointed straight at the manifest in storage: the browser talks to MinIO/S3 directly, not through any app server.

6
Streamer stops → ingest-webhook → transcode-worker

Stream ends, cleanly

OBS disconnects, MediaMTX fires runOnNotReady, the stream row flips to ended, an "ended" event goes out, and transcode-worker sends ffmpeg a SIGTERM so it finalizes the HLS playlist properly instead of leaving it dangling.

1
Streamer → web → upload-api

A file is picked and submitted

The streamer fills in their stream key and a title, and picks a video file. The web app forwards this straight through to upload-api.

2
upload-api → Postgres + MinIO

The raw file is stashed

The stream key is checked against streamers, the raw file is streamed into MinIO at raw/<video_id>.<ext>, and a videos row is created with status uploaded.

3
upload-api → Kafka

An "uploaded" event goes out

An upload.events message carries the new video_id and its raw storage key: this is the only thing that tells transcode-worker there's work to do.

4
transcode-worker

ffmpeg transcodes the whole file, once

Unlike live, there's no real-time pressure, so this runs with a slower, higher-quality preset. The video's status moves uploaded → transcoding → ready (or failed), and a transcode.status event is emitted at each step.

5
Viewer → web → MinIO

Anyone can now watch it on demand

Once ready, the video shows up on the homepage with a view count, and plays through the exact same hls.js player as a live stream. VOD and live share one playback path.

Why one ffmpeg process, not three?

You'd think making three quality levels means running ffmpeg three times. Instead, one process decodes the source once and splits it internally into three scaled outputs. That's not just an efficiency trick: HLS's adaptive switching requires every quality level to place its keyframes at exactly the same instants, and the only reliable way to guarantee that is to derive them all from one shared decode/timeline.

One file in, three qualities out

This is the "ABR ladder": the same idea as Netflix quietly dropping your picture quality on bad wifi instead of buffering. A viewer's player picks whichever rung fits their connection, and can switch mid-stream.

Kafka: five conveyor belts, not five phone calls

No service calls another service directly to say "hey, a stream just started." Instead, it drops a labeled note on the right belt, and only whoever's watching that belt reacts. That means the person who wrote ingest-webhook never had to know that a transcoder or analytics worker exists. New listeners can be added later without touching it.

stream.lifecycle"A stream started/ended," written by ingest-webhook, read by transcode-worker.
upload.events"A video was uploaded," written by upload-api, read by transcode-worker.
transcode.status"A transcode started/finished/failed," written by transcode-worker, read by analytics-worker (logged today, no aggregation yet).
viewer.analytics"Someone hit play," written by upload-api's view endpoint, read by analytics-worker, which turns it into a Postgres row.
transcode.jobsCreated for a future dispatcher stage that decouples "event happened" from "here's a transcode job," not needed yet, kept as a placeholder.
Why partitions matter later

Every topic is keyed by stream/video ID, which guarantees all events for the same stream stay in order even across multiple partitions. Right now each topic has a placeholder of 3 partitions (not sized for real load yet), but this is exactly the knob that lets Kafka spread work across many consumer instances later, which is the same mechanism Kubernetes autoscaling will hook into (more on that below).

Doesn't Kafka carry the video itself, like at Hotstar or JioTV?

No, and it doesn't there either. Kafka only ever carries small notes about what happened, never the actual video bytes. Large platforms that lean on Kafka heavily (Hotstar's own engineering writeups about scaling past 25 million concurrent viewers are well known) use it for exactly the same role as here: backend event coordination and analytics/telemetry, not video delivery. The video itself still goes out as HLS/DASH over plain HTTP from object storage and a CDN, the same shape this project uses (MinIO/S3 today, CDN explicitly deferred). Kafka's a distributed log built for one or a few consumers reading messages in order; video needs thousands of readers fetching the identical segment at once plus byte-range seeking, which is a caching problem, not a queueing one.

Where this actually runs today

Every piece above is a separate container, but today they all live on one Ubuntu box, wired together with Docker Compose. There's no cluster yet: deploying a change means copying files over with tar | ssh and running docker compose up -d --build by hand.

Honestly, the rough edges

This box is a single point of failure, schema changes are applied by hand over SSH, and there's no autoscaling: if ten streams go live at once, they all fight for the CPU of one machine and one transcode-worker process. That's precisely the set of problems Kubernetes is being brought in to solve, not novelty for its own sake.

Phase 2 · not yet built

What Kubernetes actually buys this system

Kubernetes isn't "Docker Compose but fancier." It's a control loop that constantly watches a fleet of machines and asks: is reality matching what I was told to run? If a container dies, it restarts it. If a machine disappears, it reschedules its work elsewhere. If you say "I want 5 copies of this," it makes sure there are always 5, no human on call at 2am doing that by hand. That single idea (a supervisor, not a script) is what every feature below actually is.

Mapping today's containers onto Kubernetes

Every service in docker-compose.yml has a natural Kubernetes shape. None of this needs a rewrite: it's the same containers, described differently.

Settled: one pod per live stream, not one worker juggling many

Confirmed direction for Phase 2, now written into SPEC.md. Right now transcode-worker is a single process that tracks every concurrent stream's ffmpeg subprocess in an in-memory dictionary (active_streams) using Python threads. Live streams are moving to a Kubernetes-native model instead: one dedicated Job/pod per stream, matching how most real streaming platforms isolate concurrent transcodes. Here's both models side by side, and why the second one won:

Today's model

One worker, many threads

  • A single transcode-worker replica runs one ffmpeg subprocess per active stream, tracked by a thread + a lock.
  • Scaling means running more copies of the whole worker; Kafka's consumer-group rebalancing spreads which streams land on which copy.
  • A crash in one stream's ffmpeg is isolated at the process level, but the whole worker (and every stream it's holding) shares one pod's CPU/memory budget.
  • Already warm: no cold-start latency when a new stream begins.
vs.
The Phase 2 plan

One Job/pod per live stream

  • A small Python dispatcher consumes stream.lifecycle and, on each started event, calls the Kubernetes API directly to create one dedicated Job/pod running exactly one ffmpeg process for that one stream.
  • The pod gets its own CPU/memory requests and limits, sized for exactly one stream: no noisy-neighbor risk between streams.
  • Pod count equals the number of currently-live streams, visible directly in kubectl get pods. Capacity planning becomes "how many streams, times cost-per-stream," not a guess.
  • Trade-off: a few seconds of pod-startup latency per stream, and one new small service (the dispatcher) to run, versus the always-warm existing worker.
One pod per stream, not one pod per viewer

Easy thing to assume wrong: this pod has nothing to do with how many people are watching the stream. Its only job is pulling the RTMP feed and writing HLS segments to storage, a single writer, full stop. A viewer's browser never talks to this pod at all; it fetches finished segments straight from MinIO/S3 (or a CDN later) over plain HTTP, which is a completely separate, independently scaling path. One viewer or ten thousand is identical load on the transcode pod, because object storage (not the pod) is what handles the fan-out.

Settled: this is the plan

Confirmed direction for Phase 2, now written into SPEC.md: pod-per-stream for live, driven by a small Python dispatcher calling the Kubernetes API directly (highest learning value, no new tooling), with each pod watching its own stream_id on stream.lifecycle to know when to shut itself down. VOD uploads stay on the existing shared transcode-worker pool, since each upload is already a short, self-contained job.

KEDA's job: the VOD pool, not the live path

Live streams now have a deterministic answer (one dispatcher-created pod per stream), so autoscaling isn't needed there. It's still the right tool for the shared VOD transcode-worker pool, though. KEDA (Kubernetes Event-Driven Autoscaling) watches Kafka consumer lag, how far behind a consumer group has fallen on upload.events, and adjusts replica count directly from that: more lag, more workers, and back down to zero replicas once uploads catch up. A plain CPU-based autoscaler can't do that last part, since there's nothing running yet to measure CPU on.

Two kinds of load balancing, not one

"Load balancer" means something different depending on which traffic it's carrying. The HTTP services (web, upload-api, ingest-webhook) sit behind an Ingress controller, doing ordinary L7 routing across replicas with host/path rules and TLS termination, replacing today's separate host ports. RTMP isn't HTTP, so MediaMTX needs L4 TCP load balancing instead: a NodePort or LoadBalancer Service, not an Ingress. The per-stream transcode pods need no inbound load balancing at all, since they only pull from MediaMTX and push to storage and never receive traffic themselves. And the dispatcher, if it's ever run with more than one replica for its own availability, doesn't need leader-election machinery either: it's just a normal Kafka consumer group, and Kafka's partition assignment already guarantees only one replica ever acts on a given stream.

The three-phase roadmap

Phase 2 · Next

Kubernetes (dev cluster)

  • kubeadm on the same Ubuntu box, chosen over k3s/microk8s for the deeper operator-pattern learning value
  • Kafka via the Strimzi operator
  • Postgres/MinIO as StatefulSets or Helm charts
  • transcode-worker sized from real ffmpeg benchmarks, and the pod-per-stream question resolved with real data
Phase 3 · Future

AWS (production)

  • EKS instead of self-managed kubeadm
  • Real S3, RDS for Postgres, MSK or self-hosted Kafka
  • NLB with TCP passthrough for RTMP, validated against the long-lived-connection failure class first

Known gaps worth closing first

Straight from the project's own hardening list: small, concrete, and cheap relative to the Kubernetes migration itself.

Duplicate transcodes

A redelivered Kafka message today would kick off a second transcode of the same stream/video: needs an idempotency check.

Placeholder partition counts

Every topic has 3 partitions as a stand-in, needs sizing from real throughput numbers, especially before KEDA enters the picture.

Wrong file types in storage

.m3u8/.ts files upload as generic binary today. Works with hls.js, but worth fixing before anything stricter relies on correct MIME types.

No upload limits

Anyone with a stream key can currently upload arbitrarily large or numerous files: no auth/rate-limiting yet.

Glossary

RTMP
The protocol OBS uses to push a live video feed to a server: think of it as the "upload pipe" for going live.
HLS
HTTP Live Streaming: video chopped into a few seconds of playable segments plus a manifest listing them, so a browser can fetch and switch quality like any other web file.
ABR ladder
The set of quality levels (1080p/720p/480p here) offered so a player can adapt to the viewer's connection.
GOP / keyframe
A "Group of Pictures": the chunk of video between full reference frames. It has to line up identically across every quality level for ABR switching to work.
Consumer group
A named set of Kafka readers that split up a topic's messages between them: the mechanism that lets you add more workers without double-processing anything.
Partition
A topic is split into ordered lanes; messages with the same key always land in the same lane, keeping per-stream ordering intact.
Pod
Kubernetes's smallest deployable unit, usually one container, running somewhere on the cluster.
Deployment
A Kubernetes object that keeps N identical, stateless pod copies running, replacing dead ones automatically.
StatefulSet
Like a Deployment, but for things that need stable identity and storage across restarts, for example databases or Kafka brokers.
Operator
Software that teaches Kubernetes the specific "how to run and heal this" logic for something complex. Strimzi is the Kafka operator.
HPA / KEDA
Autoscalers: HPA reacts to CPU/memory, KEDA reacts to external signals like Kafka lag, including scaling to zero.
NodePort / LB
Ways to expose a service outside the cluster: NodePort opens a fixed port on every node, and a LoadBalancer provisions a real external one.

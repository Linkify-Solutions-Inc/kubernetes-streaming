Chapter 1General Information

1-1. Scope

1-1.1 This manual describes the deployment of the kubernetes-streaming platform onto Amazon Web Services. It covers what is to be built, the order in which it shall be built, and the reasoning behind each configuration decision. It does not contain commands, configuration file listings, or console keystrokes.

1-1.2 Procedures with commands are contained in the deployment course, Modules 00 through 16. Console navigation is contained in TM SP-2. See paragraph 1-3.

1-2. Purpose of this manual

1-2.1 This manual shall be read in full before any billable resource is created. The most costly error in a deployment of this type is building components in the wrong order and discovering a dependency several layers down, at which point earlier work must be discarded.

1-3. Related publications

1-4. Advisory conventions

1-4.1 Three advisory types are used throughout this manual and TM SP-2. They are not interchangeable.

WARNING

Denotes a condition that will result in unrecoverable loss, unbounded expenditure, or loss of access to the system. Read before proceeding past the advisory.

CAUTION

Denotes a condition that will result in a failed installation step, wasted expenditure, or a fault that is difficult to diagnose later.

NOTE

Denotes supplementary information that clarifies a decision but does not, by itself, indicate a hazard.

Chapter 2Functional Description

2-1. System composition

2-1.1 Development baseline. The platform presently operates as a Docker Compose deployment: five Python services, MediaMTX, PostgreSQL, MinIO and Kafka, on one host, one network, and one configuration file.

2-1.2 Target configuration. On AWS the same system is divided across three planes. The planes shall be built in the order listed in table 2-1.

Table 2-1. Division of the system into three planes.
PlaneConstituent itemsRate of change
Account and networkAWS account, identities, VPC, subnets, routing, DNS zone, budget alarmsBuilt once. Rarely modified.
Cluster platformEKS control plane, nodes, storage driver, ingress controller, certificate automation, secrets synchronisation, autoscalerModified a few times per year.
ApplicationThe five services, MediaMTX, Kafka, transcode jobs, schema migrationsModified daily. Managed by the continuous deployment agent.

2-2. Division into three planes

2-2.1 The three planes shall be treated as separate for diagnostic purposes. They fail in different ways and are examined with different tools.

2-2.2 A pod that will not start is a plane 3 fault. A pod that starts but cannot reach the database is, in nearly all cases, a plane 1 fault. Determining the plane before beginning fault isolation eliminates the majority of wasted diagnostic effort.

Chapter 3Configuration Changes from the Development Baseline

3-1. General

3-1.1 This deployment is not a direct transfer of the existing configuration. Six components change in function, not merely in location. Each is summarised in table 3-1 and described in the paragraphs that follow.

Table 3-1. Baseline component disposition.
Baseline componentTargetReference
postgres containerRDS PostgreSQL, managed3-2
minio containerS3 bucket with CloudFront distribution3-3
kafka containerStrimzi operator, retained in cluster3-4
MediaMTX host port 1935Network load balancer, TCP passthrough3-5
transcode-worker, long-runningScaled job, one per stream3-6

3-2. Database subsystem

3-2.1 PostgreSQL transfers to RDS, which provides managed backup, failover and patching.

3-2.2 The instructional content of this step is not the creation of the instance. It is network and identity configuration: RDS resides within the VPC but outside the cluster, which requires subnet groups and security groups to be reasoned about for the first time. The first connection failure in a deployment of this type nearly always occurs here.

3-3. Object storage and content delivery

3-3.1 MinIO is replaced by S3. MinIO served as an S3-compatible substitute; no functional adaptation is required beyond endpoint configuration.

3-3.2 A content delivery network is placed in front of the bucket. HLS delivery consists of a high volume of small segment requests. If those requests are served from the cluster, both bandwidth cost and pod processor load scale with viewer count. The distribution decouples viewer count from cluster size, which is the purpose of the component.

3-3.3 The distribution shall read from a private bucket. See TM SP-2, paragraph 4-5.

3-4. Message broker

3-4.1 Kafka is retained within the cluster and installed by operator. The managed alternative carries a substantial fixed monthly charge irrespective of utilisation.

NOTE

Operating the broker by operator has instructional value beyond cost. An operator is a controller that observes custom resources and reconciles real infrastructure toward them. The same pattern recurs in the node autoscaler, the secrets controller and the continuous deployment agent. It is the most transferable concept in this platform.

3-5. Ingest path

3-5.1 RTMP is a raw TCP protocol. It cannot use hostname routing, path routing or TLS termination, all of which are functions of the application load balancer serving the web interface. A network load balancer performing TCP passthrough is therefore required as a second, separate entry point.

3-5.2 Understanding why two dissimilar load balancers are required is the principal networking lesson of this deployment.

3-6. Transcoding subsystem

3-6.1 In the baseline configuration a worker process runs continuously and consumes processor capacity while idle. The target behaviour is: a stream commences, a job is created, a node is provisioned to run it, the stream ends, the job completes, and the node is removed.

3-6.2 This change shall be performed last. It is meaningful only once the remainder of the system is confirmed operational.

3-7. Credential handling

3-7.1 The .env file is superseded. No credential shall be committed to version control.

3-7.2 A controller within the cluster reads AWS Secrets Manager and materialises Kubernetes secrets. Manifests reference secrets by name and at no point contain values.

Chapter 4Installation Sequence and Dependencies

4-1. Mandatory sequence

4-1.1 The dependencies shown in figure 4-1 are strict. Steps shall not be attempted out of sequence.

Figure 4-1. Installation dependency sequence.

4-1.2 The data layer shall be installed before the application. Every service requires at least one data component at start-up, and a service that cannot reach its database is substantially harder to diagnose than one not yet deployed.

4-2. Items that may be deferred

4-2.1 The following may be deferred or performed in parallel without obstructing the sequence:

  • Content delivery network. Direct object store access is adequate for testing.
  • Dynamic node provisioning. A fixed node group is adequate initially.
  • Continuous deployment. Manual deployment is adequate until the configuration stabilises.
  • Monitoring.

4-3. Items commonly deferred in error

CAUTION

Three items are routinely deferred and shall not be. The budget alarm incurs cost if omitted. The default storage class silently prevents Kafka from starting, presenting as an unexplained pending state. DNS delegation involves a propagation delay and an external party, neither of which can be compressed once the schedule requires them.

Chapter 5Support Data

5-1. Recurring cost

5-1.1 Approximately $240 per month with all components in continuous operation.

5-1.2 The largest single item is the EKS control plane at approximately $73 per month, fixed, incurred before any workload is scheduled. This figure governs the remaining design decisions: it is the reason a single NAT gateway is specified in place of one per availability zone, and the reason the message broker is not placed on the managed service.

5-2. Cost reduction measures

Table 5-1. Cost reduction measures in order of effect.
No.MeasureRemarks
1Scale nodes to zero when not in useControl plane, database and load balancers continue to bill. Compute is the fastest-accumulating item.
2Spot capacity for interruptible workTranscode jobs are re-runnable and are the correct workload for this. Not to be applied to continuously available services.
3NAT gateway count and traffic volumeCharged per hour and per gigabyte processed.
4Object lifecycle rulesPrevents unbounded accumulation of recorded video.

5-3. Residual billing after disposal

WARNING

Deletion of the cluster does not terminate all charges. Load balancers created by Kubernetes objects, content delivery distributions, object versions, orphaned volumes and unassociated addresses all persist and continue to bill.

Disposal shall be verified against the cost-by-service report one to two days after teardown. A console resource list is not sufficient verification, as it will not show what was not looked for. Disposal procedure is given in TM SP-2, chapter 6.

5-3.1 Disposal shall be planned before construction begins. Where infrastructure was created from a configuration file, disposal is a single operation followed by a manual sweep. Where infrastructure was created by hand, disposal becomes an exercise in recollection.

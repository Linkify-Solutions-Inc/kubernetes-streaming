01

Key-based SSH, without breaking what was there

laptop → box

The starting position was a password in a .env file. Two constraints made this less trivial than ssh-copy-id usually is: the fatima account already had one authorized key that had to survive, and the password could not be allowed to leak into shell history or the process table.

Why a dedicated key — the laptop already held five keys for other hosts, including one for aayush@100.64.0.9 — the same box, a different account. Reusing that key would have merged two identities that are deliberately separate. A per-account key also means revoking access to fatima later is a one-line change that touches nothing else.
generate
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_intern-fatima -N "" \
  -C "aayush@macbook -> fatima@aayush-InternServer"

ssh-copy-id is the right tool because it appends to authorized_keys and refuses to install a key that is already present — it cannot clobber the existing entry. The problem is that it prompts for the password interactively. sshpass was not installed, so macOS's built-in expect drove the prompt instead, reading the password from an environment variable rather than from argv:

copyid.exp — deleted immediately afterwards
#!/usr/bin/expect -f
set timeout 30
set pw $env(SRV_PW)
spawn ssh-copy-id -o StrictHostKeyChecking=accept-new \
  -o PreferredAuthentications=password -o PubkeyAuthentication=no \
  -i [lindex $argv 0] [lindex $argv 1]
expect {
    -re "(?i)password:" { send "$pw\r"; exp_continue }
    eof
}
Why those two -o flags — without PreferredAuthentications=password and PubkeyAuthentication=no, SSH would try every key in the agent first. On a box that already trusts one of those keys, it could authenticate silently and the expect block would sit waiting for a password prompt that never arrives, until it times out.
Verified — reading authorized_keys back showed both entries: the pre-existing fatima@streaming-project key and the new one. The comment field is what makes this checkable at a glance, which is the whole reason for setting -C.

Finally an alias, so the account is addressable by name. The existing Host 100.64.0.9 block still maps to aayush and was left untouched — SSH matches Host patterns literally, so the two blocks never collide. 

Host intern-fatima
  HostName 100.64.0.9
  User fatima
  IdentityFile ~/.ssh/id_ed25519_intern-fatima
  IdentitiesOnly yes
02

Passwordless sudo, installed safely

on the box

kubeadm is almost entirely privileged work — writing to /etc/kubernetes, restarting containerd, editing sysctls, loading kernel modules. A password prompt in the middle of that is not just annoying, it breaks non-interactive automation outright.

The risk — a syntactically invalid file in /etc/sudoers.d/ can break sudo for everyone on the machine, and the usual way to fix that is sudo. On a box with four other user accounts, that is a genuinely bad outcome.

So the file is validated before it is placed, not after. It is written to /tmp, checked with visudo -cf, and only then installed with the correct mode and ownership in one atomic install call: 

echo "fatima ALL=(ALL) NOPASSWD:ALL" > /tmp/.sudoers-fatima
visudo -cf /tmp/.sudoers-fatima          # parse before installing
install -m 0440 -o root -g root /tmp/.sudoers-fatima \
  /etc/sudoers.d/90-fatima-nopasswd
rm -f /tmp/.sudoers-fatima
visudo -c                                 # re-verify the whole tree

The password for this one bootstrapping call was piped over the SSH channel directly into sudo -S, which reads it from stdin. It never appears in argv, so it is invisible to ps on the remote host, and it never touches shell history on either end.

Found while verifying — the final visudo -c flagged a pre-existing, unrelated file: /etc/sudoers.d/interns has mode 0644 instead of 0440. sudo silently ignores any file in that directory with loose permissions — so whatever privileges that file was meant to grant have never been in effect. Left alone, since it belongs to someone else's setup, but worth someone knowing.

04

Host preflight

on the box

Three changes, each fixing a specific way the kubelet or the pod network would otherwise fail.

Swap off, permanently

Why — the scheduler's whole model assumes a pod's memory request maps to real RAM. Swap breaks that: a pod that should be evicted instead gets silently paged to disk, and latency-sensitive work — like an ffmpeg transcode holding a live stream — degrades in a way no metric obviously explains. Kubernetes' answer is to refuse to run at all. 
sudo swapoff -a
sudo sed -i.bak '/\sswap\s/s/^/#/' /etc/fstab   # survives reboot

The sed is the load-bearing half. swapoff -a alone lasts until the next boot, at which point the kubelet would refuse to start and the cluster would come back dead.

Kernel modules

Why — overlay is the filesystem driver containerd layers images with. br_netfilter is what makes bridged traffic traverse iptables at all — without it, kube-proxy's Service rules exist but never match anything, and Services fail in a way that looks like a DNS problem. 
printf 'overlay\nbr_netfilter\n' | sudo tee /etc/modules-load.d/k8s.conf
sudo modprobe overlay && sudo modprobe br_netfilter

sysctls

net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1

The first two activate what br_netfilter makes possible. ip_forward lets the host route between interfaces at all — required for pod-to-pod traffic, and it turns out to be required again in step 12 for an entirely different reason.

Verified — swapon --show empty, lsmod lists both modules, sysctl reads back 1 for all three.
05

containerd — the one Docker already installed

on the box

Docker does not implement Kubernetes' Container Runtime Interface; that is why dockershim was removed back in v1.24. But Docker ships containerd, which does implement CRI. The box already had containerd 2.2.5 running underneath dockerd.

Inspecting its config explained why kubeadm couldn't see it:

disabled_plugins = ["cri"]

Docker deliberately disables the CRI plugin, because Docker doesn't use it and leaving it on would expose an unauthenticated container-creation API. Two options followed: install a second containerd alongside the first, or enable CRI on the existing one.

Why reuse it — two containerd instances means two image caches, two sets of snapshots, and double the disk for images used by both. It also creates a genuinely confusing failure mode where docker images and crictl images disagree about what exists on the box. One runtime, two clients, is the cleaner model — and it is what a managed node does anyway. 
# keep Docker's original, then regenerate from scratch
sudo cp /etc/containerd/config.toml /etc/containerd/config.toml.docker-orig
sudo sh -c 'containerd config default > /etc/containerd/config.toml'
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
sudo systemctl restart containerd
Why SystemdCgroup = true — Ubuntu boots with systemd as the sole writer of the cgroup tree. If containerd also writes to it directly (the cgroupfs driver), two managers end up with different views of the same resource limits. The documented symptom is instability under memory pressure — which is exactly the condition a box running concurrent transcodes lives in. kubelet defaults to the systemd driver, so the runtime has to match.
Verified — config regenerated at version = 3 with disabled_plugins = []. Both containerd and docker reported active after the restart, and the sandbox image in the config (registry.k8s.io/pause:3.10.1) matched what kubeadm config images list expects — a mismatch there causes every pod to pull a second pause image.
06

Picking a Kubernetes version

decision

Latest stable was v1.36.3. The cluster runs v1.35.7, one minor behind, on purpose.

The constraint is not Kubernetes itself but everything that has to sit on top of it. Calico v3.32 — the current release — documents testing against Kubernetes 1.34, 1.35 and 1.36. Picking 1.35 lands in the middle of that window rather than at its edge, which leaves room for MetalLB, KEDA and Strimzi, all of which have to be added later and none of which certify against a brand-new minor on day one.

Why not just take latest — on a learning cluster, time spent debugging a genuine ecosystem incompatibility teaches you about that specific bug, not about Kubernetes. One minor of slack buys out most of that class of problem for free. 
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
Why the hold — an unattended apt upgrade that bumps kubelet a minor version out from under a running control plane is a well-known way to break a cluster. Kubernetes upgrades are a deliberate, ordered procedure — apt-mark hold makes sure they stay deliberate.
07

kubeadm init, from a config file

on the box

Everything went into k8s/cluster/kubeadm-config.yaml rather than a line of CLI flags. A config file is diffable, reviewable, and — because it is committed — it answers "why is the pod CIDR that?" six months from now without anyone having to reconstruct a shell command from memory.

The three decisions embedded in it

FieldValueReasoning
advertiseAddress 10.50.0.2 Must be a real routable interface address. The Tailscale IP is a /32 with no subnet — usable as a cert SAN, but not as the address the control plane binds and advertises.
podSubnet 192.168.0.0/16 The only large private block not already spoken for. 10.x collides with the LAN; 172.16–31.x collides with Docker's four bridges. An overlap here produces intermittent, extremely confusing routing failures.
nodeRegistration.name aayush-internserver The hostname has capitals; node names must be lowercase RFC-1123. Pinned explicitly instead of relying on kubeadm to normalise it.

Certificate SANs — the part that pays off later

apiServer:
  certSANs:
    - 10.50.0.2
    - 100.64.0.9                              # Tailscale
    - aayush-internserver.hs.aayushpathak.com  # MagicDNS
    - localhost
    - 127.0.0.1
Why this matters — TLS certificates are bound to the names they were issued for. An API server certificate that only lists 10.50.0.2 will be rejected by kubectl connecting to 100.64.0.9, even though it is the same machine. Adding SANs afterwards means regenerating the certificate and restarting the control plane. Adding them at init time costs nothing.

--dry-run first — it runs every preflight check and renders the full manifest set without writing anything permanent. Then the real thing: 

sudo kubeadm config images pull --config kubeadm-config.yaml
sudo kubeadm init --config kubeadm-config.yaml

Pulling images separately is worth the extra line: it separates "the registry is unreachable" from "the cluster failed to initialise", which otherwise arrive as the same timeout.

Result — control plane up in about 20 seconds. etcd 3.6.6, apiserver, scheduler and controller-manager all Running; CoreDNS Pending, which is correct — there is no pod network yet for it to attach to.
08

Removing the control-plane taint

on the box

kubeadm taints the control-plane node NoSchedule by default, so ordinary workloads never land on the machine running etcd. On a multi-node cluster that is exactly right. On a one-node cluster it means nothing can ever be scheduled. 

kubectl taint nodes --all node-role.kubernetes.io/control-plane-

The trailing - is the removal syntax, and it is easy to miss when reading.

Trade-off worth naming — this genuinely removes a safety property. A transcode pod that exhausts memory now sits on the same node as etcd, and etcd is latency-sensitive enough that heavy neighbours can cause leader elections. This is precisely why the resource requests/limits on the transcode workload — sized from the ~2.3 cores / ~1 GiB benchmark — stop being optional once real workloads land.
09

Calico — the pod network

on the box

Until a CNI plugin is installed the node reports NotReady and CoreDNS stays Pending. Kubernetes deliberately ships no default: it defines the interface and leaves the implementation open.

Why Calico over Flannel or Cilium — Flannel is the simplest, but implements no NetworkPolicy at all, which would leave half of Kubernetes networking untaught and every pod able to reach every other pod forever. Cilium's eBPF dataplane is the most interesting technically, but adds a second novel system to debug at the same time as the cluster itself. Calico supports NetworkPolicy properly, is the most common kubeadm pairing (so its failure modes are well documented), and is closest to what EKS will look like in Phase 3.
Where this failed the first time — applying the operator and then the Installation CR — the sequence in most tutorials — produced no matches for kind "Installation" in version "operator.tigera.io/v1". In Calico 3.3x the CRDs were split into a separate operator-crds.yaml manifest. The operator deployment alone no longer registers the types it consumes, so the CRDs must be applied first. 
kubectl create -f .../v3.32.1/manifests/operator-crds.yaml     # first
kubectl create -f .../v3.32.1/manifests/tigera-operator.yaml
kubectl -n tigera-operator rollout status deploy/tigera-operator
kubectl create -f calico-installation.yaml

The Installation CR sets encapsulation: VXLANCrossSubnet — encapsulate only when traffic crosses a subnet boundary. On one node nothing does, so pod traffic stays unencapsulated and pays no VXLAN overhead, while the setting is already correct if a second node is ever joined.

Verified — kubectl get tigerastatus showed all four components Available=True, Degraded=False. The node flipped to Ready and both CoreDNS pods picked up addresses in 192.168.115.0/24 — a /26 block carved from the configured pod CIDR, exactly as intended.
10

MetalLB — making type: LoadBalancer mean something

on the box

On a cloud provider, creating a LoadBalancer Service triggers a controller that calls the provider's API and provisions a real load balancer. On bare metal there is no such controller, so the Service sits at EXTERNAL-IP: <pending> forever. MetalLB fills that role.

Why bother, when NodePort exists — MediaMTX's RTMP port is not HTTP, so it cannot go behind an Ingress — it needs L4. NodePort would work, but only on ports 30000–32767, and the manifests would then have to be rewritten for Phase 3 where a real cloud load balancer is available. MetalLB makes the Phase 2 manifest identical to the Phase 3 one: type: LoadBalancer, port 1935. The mechanism underneath changes; the declaration does not.

Choosing the pool

MetalLB needs IPs it can claim on the local segment. This is where the earlier ping sweep pays off: the entire 10.50.0.0/24 contained exactly two hosts, so the top /28 — 10.50.0.240 through .254 — is demonstrably free rather than assumed free. 

apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata: { name: lan-pool, namespace: metallb-system }
spec:
  addresses: [ 10.50.0.240-10.50.0.254 ]

L2 mode rather than BGP: BGP requires a router willing to peer, and the gateway here is not under our control. In L2 mode one node answers ARP for each pool address, so from the LAN's perspective the IP simply appears on the network.

One check worth doing — MetalLB's L2 mode requires strictARP: true when kube-proxy runs in IPVS mode. This cluster's kube-proxy is in the default iptables mode, where the setting is not needed — confirmed by reading the kube-proxy ConfigMap rather than assuming the default.
11

ingress-nginx — L7 routing

on the box

Three of the five services — web, upload-api, ingest-webhook — are plain HTTP and can share one entry point, routed by host and path. That is what an Ingress controller does, and it replaces the separate host ports each service binds under Compose today.

The variant matters — ingress-nginx publishes several deployment manifests. The baremetal one creates a NodePort Service; the cloud one creates a LoadBalancer Service. Because MetalLB is installed, cloud is the correct choice here — the intuitive-sounding "baremetal" would bypass the load balancer that was just set up.
Verified — the Service moved from <pending> to 10.50.0.240 within seconds, which is itself the proof that MetalLB's controller is working. 
NAME                       TYPE           EXTERNAL-IP   PORT(S)
ingress-nginx-controller   LoadBalancer   10.50.0.240   80:32091/TCP,443:31550/TCP
12

The routing problem that nearly sank it

the interesting one

At this point the cluster worked and curl http://10.50.0.240/ returned nginx's default backend — from the box. From the MacBook it timed out.

The reason is a mismatch nothing had forced into the open yet:

  • Every human and every OBS client reaches this box over Tailscale, at 100.64.0.9.
  • Tailscale advertises that address as a bare /32 — one host, no subnet behind it.
  • MetalLB hands out addresses on 10.50.0.0/24, a network that exists only on the far side of that /32.

So the laptop had no route to 10.50.0.240 at all. Every LoadBalancer IP the cluster could ever assign was, from the perspective of every actual user, invisible.

The fix — make the box a Tailscale subnet router for exactly the pool range, so the tunnel carries a route to those fifteen addresses and nothing else. 
sudo tailscale set --advertise-routes=10.50.0.240/28

tailscale set rather than tailscale up: up re-applies the entire preference set from its flags, silently resetting anything not restated on the command line. set changes one preference.

Advertising only /28 rather than the whole /24 is deliberate: nothing on the tailnet gains a route to the gateway or to anything else that might later appear on that LAN.

Does this actually work? MetalLB L2 is ARP-based

This deserved checking rather than assuming, because the two mechanisms appear to conflict. MetalLB L2 works by answering ARP requests for pool addresses — but a packet arriving through the Tailscale tunnel never triggers an ARP resolution on the LAN. If MetalLB's ARP responder were the only thing making those IPs work, subnet-routed traffic would fall straight through.

It works, and the reason is that ARP is not what does the work:

Packet path — laptop to a LoadBalancer IP
dst 10.50.0.240:80enters on tailscale0
↓   ip_forward = 1, so the host is willing to forward   ↓
netfilter — nat table, PREROUTING
KUBE-SERVICESmatches on destination IP only
DNAT→ 192.168.115.x:80 (a pod)
↓   routing decision happens after DNAT   ↓
Delivered
Calico veth → podnever reaches the LAN, never ARPs

kube-proxy's iptables rules live in PREROUTING and match purely on destination address — they do not care which interface the packet arrived on. A forwarded packet is rewritten to a pod IP before the kernel makes its routing decision, so it is never sent out onto ens18 and no ARP resolution is ever needed. MetalLB's ARP responder only matters for hosts physically on the 10.50.0.0/24 segment. The two mechanisms are independent paths to the same iptables rules.

Still outstanding — advertising a route is a request, not a grant. It must be approved in the Tailscale admin console before any peer receives it. Until then 10.50.0.240 answers only from the box itself — confirmed, as it currently still times out from the laptop. The reasoning above is verified; the end-to-end path is not, and cannot be until that approval happens.

kubectl from the laptop

laptop

The API server is a different matter from LoadBalancer IPs — it listens on 10.50.0.2:6443, but the kubelet binds 0.0.0.0, so it is already reachable at 100.64.0.9:6443 over Tailscale. The only thing needed was the certificate SAN added back in step 7.

So the entire remote-access setup is: copy the admin credentials, rewrite one URL, merge. 

ssh intern-fatima 'sudo cat /etc/kubernetes/admin.conf' > /tmp/admin.conf
sed -i '' 's|https://10.50.0.2:6443|https://100.64.0.9:6443|' /tmp/admin.conf
KUBECONFIG=~/.kube/config:/tmp/admin.conf kubectl config view --flatten > /tmp/merged
cp ~/.kube/config ~/.kube/config.bak-$(date +%Y%m%d-%H%M%S)
install -m 600 /tmp/merged ~/.kube/config
rm -f /tmp/admin.conf /tmp/merged
Why the merge dance — the laptop already had a kind-streamly context. Overwriting ~/.kube/config would have silently destroyed it. config view --flatten across a KUBECONFIG list is the supported way to combine them, and the timestamped backup exists because merges are easier to undo than to debug.
Verified — both contexts present, and kubectl get nodes against context streaming-k8s returns the node over Tailscale from the MacBook with no tunnel, proxy or SSH hop.
Minor — the laptop's kubectl is v1.34.1 against a v1.35.7 server. That is within the supported ±1 minor skew, so it works, but it is worth bringing up to match.

What's open

next

Needs a human

  • Approve the Tailscale subnet route — 10.50.0.240/28 on aayush-internserver. Until this happens no LoadBalancer IP is reachable off-box. Verify with curl -I http://10.50.0.240/ from the laptop; a 404 from nginx's default backend is success.
  • Upgrade the laptop's kubectl to 1.35 to match the server.
  • /etc/sudoers.d/interns is mode 0644 and therefore being ignored entirely by sudo. Pre-existing, unrelated, and not ours to change — but someone probably believes it is working.

Blocking the next stage

No StorageClass exists yet — nothing in this build provisions storage. The next stage begins with Postgres, MinIO and Kafka, all of which want PersistentVolumeClaims — and every one of them will sit in Pending forever with no provisioner installed. On a single node the straightforward answer is the local-path provisioner; that decision should be made before any StatefulSet is applied, not after.

Then, in dependency order

  1. Kafka via Strimzi — operator plus Kafka/KafkaTopic CRs, KRaft mode, with the partition counts KEDA's ScaledJob concurrency depends on.
  2. Postgres and MinIO as StatefulSets.
  3. The three HTTP services as Deployments behind the Ingress that already exists; MediaMTX via the L4 LoadBalancer shape rehearsed above.
  4. Secrets via SOPS — the current .env has already caused one real outage through silent drift.
  5. transcode-worker as two KEDA ScaledJobs — the one item here that is a genuine code change, not a deployment change: today's persistent while True consumer loop has to become a one-shot entrypoint that handles a single unit of work and exits.
Stage 1 complete

A single-node kubeadm cluster on Kubernetes v1.35.7, with Calico providing pod networking and NetworkPolicy, MetalLB making type: LoadBalancer real on bare metal, and ingress-nginx handling L7 — driveable from a laptop over Tailscale.

Reproducing it takes k8s/cluster/README.md; the reasoning behind each choice lives in SPEC.md under Phase 2 cluster. Nothing here is a workload yet — that starts with storage.
